## Why

The kit has strong structural validators and provider-free component proofs, but no maintained current-candidate gate demonstrates that the loaded workflow improves a representative unrelated project without weakening outcome, proof, safety, or owner authority. This allows green proxy checks and stale qualification evidence to coexist with an unproven or regressed consumer experience.

## Outcome Capsule

- **Outcome**: A maintainer can run one versioned matched baseline/candidate workflow over fixed unrelated disposable consumer scenarios and obtain a deterministic result showing equivalent accepted outcomes and safety plus either exact friction no-regression or, when explicitly selected for an optimization claim, at least one strict friction reduction.
- **Operating Envelope**: Two fixed non-sensitive disposable consumer repositories with different workflow shapes; the current increment uses three baseline samples per scenario, at most six configured-primary requests total, to establish the first accepted baseline. A later model-facing candidate may run the complete three-sample baseline/candidate comparison under a separate explicit bound of at most twelve requests. Both use the same configured model route, prompts, environment, initial state, and validation adapters; replay and normal validation are provider-free.
- **Non-Goals**: Optimizing the default instruction surface; changing skill or agent routing; fixing current active OpenSpec changes; adding Windows CI; benchmarking runtime scalability; proving every technology stack or model; using elapsed time or token estimates as the sole acceptance oracle; running captures on consumer or production repositories.
- **Non-Deferrable Invariants**: Candidate outcome, validation, proof, protected-boundary behavior, cleanup, and forbidden-effect results cannot be weaker than baseline; baseline and candidate identities and inputs must be comparable; evaluator logic cannot infer semantic quality or hide unknown facts; configured-provider capture requires the existing bounded synthetic-call authority; secrets, private prompts, and absolute private paths cannot enter retained evidence.
- **Observable Proof**: Establish the current accepted kit as the first baseline through the installed OpenCode entry point on both disposable scenarios, replay its immutable bundles without provider calls, and show through controlled candidate fixtures that the evaluator rejects an outcome regression, a safety regression, a stale identity, a new owner question, an added model call, an added failed/repeated tool attempt, and an optimization candidate with no strict friction improvement; a no-regression fixture and a strictly improved fixture pass with complete cleanup.
- **Material Residual Risks**: Fixed synthetic scenarios may not predict every project or model; exact call-count improvements can incentivize overly narrow optimization; configured-provider availability can block fresh capture while provider-free replay remains usable; a later model or OpenCode version changes the environment identity and requires recapture.
- **Stop Line**: Finish when one project-neutral capture/replay/evaluator tool, one reviewed scenario manifest, package integration plus one provider-free step in the existing Ubuntu validation workflow, proof inventory documentation, and a current installed baseline plus controlled no-regression/improvement evaluator evidence are green. Do not add Windows/template CI, optimize instructions, add scenario families, alter unrelated active changes, or claim universal productivity improvement in this increment.

## What Changes

- Add a project-neutral consumer outcome regression capability with explicit scenario, environment, candidate, evidence, and evaluator schemas.
- Add two fixed disposable scenario shapes: one Ordinary Small repository without OpenSpec ownership and one OpenSpec-backed repository with bounded planning/apply behavior.
- Add matched installed capture for baseline and candidate using the same model route, input, environment, validation argv, permissions, and initial fixture state.
- Add provider-free replay and deterministic evaluation that treats correctness and safety as hard invariants and exact friction counts as a Pareto no-regression vector; an explicit `improvement` expectation additionally requires at least one strict count reduction, while `no-regression` never claims improvement.
- Add a one-time baseline-establishment result so the measurement capability can be introduced without fabricating an improvement over identical model-facing behavior.
- Add candidate/source/environment freshness checks so archived evidence cannot validate changed runtime artifacts.
- Add the replay/evaluator lane to project-native validation and the existing Ubuntu validation workflow; document configured-provider capture as an explicit, separately authorized evidence refresh rather than a CI side effect. Windows CI and consumer workflow templates remain unchanged.

## Capabilities

### New Capabilities

- `library-consumer-outcome-regression`: Defines matched consumer scenarios, capture/replay evidence, deterministic no-regression and strict-improvement oracles, candidate freshness, privacy, cleanup, and validation integration.

### Modified Capabilities

None. Existing active changes retain their current capability ownership and must be reconciled separately.

## Impact

- New project-neutral proof/evaluator tooling under `tools/proofs/` with shared support only when repeated exact contracts justify it.
- New reviewed scenario and threshold manifest under repository-owned config or proof fixtures.
- Package scripts, proof inventory, focused tests, strict validation routing, and CI provider-free replay/evaluation.
- Fresh disposable OpenCode sessions and bounded configured-provider calls only during explicit capture; no install, activation, consumer migration, remote repository operation, or production deployment.
