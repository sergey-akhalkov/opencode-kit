## Why

The kit can stop materially similar retries and capture workflow friction, but it does not require an active session to reconsider its delivery route when different defects keep appearing at the same late boundary or measured repeated setup dominates the remaining work. As a result, an agent can make locally rational corrections while the accepted outcome remains at the same downstream boundary until the user interrupts and asks why progress is slow.

## Outcome Capsule

- **Outcome**: Every installed kit primary session can recognize evidence-backed delivery drag in any project or task class, pause only the next dependent costly action, perform one bounded outcome-preserving delivery checkpoint, autonomously adopt the smallest safe route improvement, and continue accepted work without waiting for a user prompt. OpenSpec and grind-backed work preserve the route decision in their existing planning/frontier owners; reusable cross-project friction may be reported separately to Kaizen without making Kaizen the current-task scheduler.
- **Operating Envelope**: Loaded global main instructions and maintained OpenSpec apply behavior on the supported OpenCode runtime; Ordinary Small and Material work; ordinary, OpenSpec, and explicitly grind-enabled parentless roots; facts from current tool results, task/frontier state, observed wall time, current-run diagnostics, and reviewed dependency identities; one checkpoint per unchanged bottleneck identity; no deterministic semantic scoring or background scheduler.
- **Non-Goals**: Periodic time-based interruption, universal duration estimates, optimizing checkbox counts, weakening accepted scope or proof, replacing project planning, automatically reducing a test or evidence population, bypassing live-attempt or protected-action gates, mandatory specialist/reviewer calls, autonomous cross-project mutation, a generic workflow database, or guaranteeing that every possible bottleneck is detected.
- **Non-Deferrable Invariants**: Outcome, operating envelope, accepted population, quality, safety, authorization, restoration, cleanup, and evidence claims remain unchanged unless the owner makes an otherwise required protected product decision. A long operation, unchanged task count, single cheap failure, or new useful evidence alone is not delivery drag. The checkpoint blocks only its dependent costly action, never clears a Live-Attempt Gate or another scoped gate, never treats sibling success as evidence for the blocked lane, never converts a process decision into an owner question, and never repeats for an unchanged bottleneck without decision-changing evidence.
- **Observable Proof**: Through the installed configured kit in unrelated disposable projects, exercise at least: materially similar no-progress retries; materially different failures discovered only after the same costly late boundary; repeated proof-owner churn that invalidates an unchanged long chain; a measured dominant serial setup cost; a legitimately long but advancing task; and an irreducible-cost task with no safe optimization. Observe one bounded checkpoint only for supported delivery-drag cases, autonomous selection of an outcome-preserving shift-left/isolation/automation route, unchanged outcome and proof population, task-scoped continuation, no user question, duplicate suppression, and normal continuation for controls. In an OpenSpec root observe coherent `history.md`/planning updates only when the route changes; in a grind root observe a process item that blocks only the dependent action while independent runnable work drains.
- **Material Residual Risks**: Model-owned trigger classification can miss a bottleneck or over-trigger; route changes can hide an unrecognized behavioral-substitution claim; instruction-only ordinary sessions lack deterministic semantic enforcement; extra reflection can itself add latency; supplied dependency identities can be stale; and active changes currently overlap global instruction, OpenSpec apply, completion-frontier, compaction, and Kaizen surfaces.
- **Stop Line**: Finish one universal evidence-backed trigger and bounded checkpoint contract, ordinary/OpenSpec/grind routing, outcome-preserving option and owner-boundary rules, duplicate suppression, concise continuity fields, focused deterministic contract checks, and installed cross-project behavior proof. Stop before timers, velocity scoring, autonomous scope reduction, generic optimization planning, background triage, new persistence services, automatic provider calls, project-specific heuristics, or implementation of optimizations in consumer projects.
- **Delivery Horizon:** none - this is a universal kit lifecycle correction and is not part of a declared product delivery horizon.

## Claim And Evidence Scope

- **Claim ID**: `OPDC-001`
- **Claim Class**: Finite-population installed workflow behavior across project-neutral task classes.
- **Population**: Reviewed ordinary, OpenSpec, and grind scenarios covering similar-retry stagnation, different-defect late-discovery loops, repeated evidence-chain invalidation, measured dominant setup cost, advancing long work, irreducible cost, duplicate bottleneck identity, independent sibling work, owner-owned scope/proof changes, and compaction continuity.
- **Coverage Basis**: Provider-free disposable fixtures plus matched configured installed sessions in at least two unrelated disposable repositories, using the same accepted outcomes and oracles for comparison, with exact prompt/tool/question/task/frontier/file/effect observations.
- **Production Path**: Loaded global main authority, canonical OpenSpec apply skill, compaction continuity contract, existing grind frontier/completion guard, and optional explicit Kaizen reporting.
- **Comparison Paths**: Current stagnation-only behavior, an advancing long-running task, a single cheap failure, an unchanged bottleneck replay, a route with no safe optimization, and a proposed optimization that would narrow accepted evidence.
- **Environment**: Current supported OpenCode and installed kit source on local Windows, provider-free fixtures, bounded configured synthetic sessions in disposable Git/OpenSpec roots, isolated OpenCode state, and no consumer-project remote or protected effect.
- **Real Oracle**: Ordered assistant/tool/question events, exact current task/frontier state, observed wall-time facts and current-run diagnostics, selected route and suppression identity, changed planning/history paths, absence of unapproved scope/proof changes, continuation markers, and process/session cleanup.
- **Unresolved Observations**: Trigger quality outside the reviewed population, behavior in untested OpenCode/model versions, bottlenecks whose cost cannot be observed safely, optimization opportunities requiring unproved substitution equivalence, and ordinary non-grind sessions where instruction compliance is the only enforcement layer.
- **Maximum Claim**: In the reviewed installed environment and finite scenario population, the kit prompts and, where grind is enabled, enforces one bounded route reconsideration when current evidence establishes delivery drag, while preserving accepted outcome and proof and avoiding a user question. It does not guarantee optimal scheduling, universal bottleneck detection, elapsed-time reduction in every task, or safe reuse/batching without separate equivalence evidence.

## Automation Dividend

- **Automation Dividend**: required - extend the existing instruction/compaction and completion-guard proof owners with one reviewed project-neutral scenario pack and evaluator that verifies trigger discrimination, checkpoint boundedness, route selection, duplicate suppression, task-scoped grind projection, planning continuity, and absence of scope/proof weakening without deterministic semantic scoring.
- **Bounded Falsification Review**: required - universal trigger boundaries, false-positive controls, current-task versus Kaizen ownership, autonomous route authority, behavioral-substitution escape, ordinary/OpenSpec/grind consistency, duplicate suppression, and observable installed proof.

## What Changes

- Add one universal outcome-preserving delivery-checkpoint contract that distinguishes repeated-strategy stagnation from different-defect late-discovery and measured dominant-cost patterns.
- Extend loaded main and compaction continuity instructions so a current session performs the checkpoint before another dependent costly action and carries an unresolved checkpoint across compaction without turning it into optional future work.
- Extend OpenSpec apply behavior so a confirmed route change updates only the necessary design, tasks, stop line, and strategy history as autonomous process controls, then continues implementation.
- Reuse the grind task-scoped frontier to represent the checkpoint as a process item or gate dependency, requiring independent runnable work to continue and preventing a process checkpoint from becoming a product question.
- Keep Kaizen as optional cross-project signal transport after the current route is handled; it neither authorizes nor schedules the checkpoint.
- Add provider-free and installed multi-project scenario checks that compare the current stagnation-only path with the candidate behavior and protect long-but-advancing and irreducible-cost controls.

## Capabilities

### New Capabilities

- `outcome-preserving-delivery-checkpoints`: Defines evidence-backed delivery-drag triggers, bounded route reconsideration, autonomous outcome-preserving optimization, suppression, owner boundaries, and project-neutral proof.

### Modified Capabilities

- `library-instruction-artifacts`: Makes current-session delivery checkpoints and their compaction continuity part of the loaded main instruction behavior without adding periodic retrospectives.
- `library-spec-workflow-integrity`: Requires OpenSpec apply to preserve and execute a confirmed outcome-preserving route correction through existing design/task/history controls.
- `session-completion-guard`: Requires grind frontiers to keep a due delivery checkpoint task-scoped, drain independent work, and reject process-checkpoint escalation as a product decision.

## Impact

- Primary owners: `global/AGENTS.md`, the managed compaction prompt/template, `global/skills/openspec-apply-change`, existing instruction and OpenSpec contract validators, and the session-completion-guard scenario/proof family. Exact production paths remain implementation decisions after current ownership recheck.
- The current owners are extended rather than replaced: stagnation remains the retry owner, Change-Ready remains the costly-proof and substitution-routing owner, OpenSpec artifacts remain planning controls, grind remains task-scoped enforcement, and Kaizen remains non-authorizing signal transport. The new capability owns only the missing cross-cutting delivery-checkpoint semantics.
- No consumer-project code, test population, evidence population, persisted product data, public API, remote system, installation, or runtime activation is changed by planning this proposal.
- Profile: `Material` because later implementation changes loaded instruction/compaction lifecycle behavior and grind continuation policy. Planning remains development-only and grants no install, restart, provider-cost expansion, protected action, commit, push, release, or deployment authority.
