## Goals / Non-Goals

**Goals:**

- Make accepted outcome scope distinct from implementation sequencing.
- Require the main session to select the next task slice from declared order, dependencies, safety/proof gates, and the earliest real boundary.
- Prevent owner menus for task ranges, batch size, optional review, or current-cycle duration when the user requested the active change and did not bound the request more narrowly.
- Preserve exact owner questions for changed accepted semantics and protected decisions/actions.

**Non-Goals:**

- No task scheduler, duration estimator, or general semantic classifier.
- No permission to bypass dependency, safety, proof, validation, interruption, or protected-action gates.
- No automatic work beyond an explicit user task limit.
- No installation, activation, remote change, or historical archive rewrite.

## Decisions

### 1. Narrow the existing ambiguity rule instead of adding another priority

The global rule will ask only when ambiguity can materially change accepted outcome, operating envelope, non-deferrable invariants, material risk, data/public API behavior, or another protected semantic decision. Implementation order, task batching, tool choice, optional review, and current-cycle size are explicitly not owner scope.

Alternative: add another broad "be autonomous" sentence. Rejected because broad reminders already exist and did not eliminate the conflict; removing the overloaded meaning of `scope` is smaller and easier to retrieve.

### 2. Use existing task evidence for deterministic sequencing

For an already selected apply change, unchecked ordinary and admitted improvement tasks are accepted implementation work unless the user explicitly bounded the current request. Main selects the smallest dependency-valid next slice that reaches the earliest safe real boundary, then continues through remaining work after proof and validation. Task file order is the fallback when dependencies and gates do not impose another order.

Alternative: always execute the largest available batch. Rejected because it delays real feedback and increases invalidation. Alternative: always ask after each task group. Rejected because batch size is process control, not a product decision.

### 3. Keep the fallback arbiter aligned

The hidden completion arbiter will classify a menu among in-scope task ranges or optional review as autonomous and choose only an offered option that safely advances the next dependency-valid slice. It will retain `owner_required` when every advancing option crosses an exact owner boundary.

Alternative: rely only on the arbiter. Rejected because the primary should not create avoidable questions, and grind mode is optional.

### 4. Validate structure and loaded behavior separately

Focused contracts will pin the sequencing/owner-boundary pair on canonical apply and arbiter surfaces. A fresh configured primary-session proof will use the reported multi-batch state plus a paired protected-action case. Static markers do not claim model effectiveness.

Alternative: deterministic keyword checks alone. Rejected because the repository specification requires same-model loaded workflow evidence for instruction behavior.

### 5. Settle hidden route readiness without retrying model work

Hidden agent/provider discovery will retry only the provider-free route lookup for a short finite startup window. It creates no child and invokes no model until the route is complete. Interruption cancels the settle wait. Exhaustion preserves the existing capability failure, so a permanent missing agent/provider/model remains fail-closed and does not enter the arbiter verdict retry loop.

Alternative: classify every missing route as a transient audit failure. Rejected because permanent configuration mismatch would consume model-oriented retries and blur the existing capability contract. Alternative: warm only the proof runner. Rejected because the observed failure is in production guard startup and can affect a real first question.

## Risks / Trade-offs

- **Over-broad sequencing could ignore a real product choice** -> The narrowed ambiguity rule retains accepted-outcome, operating-envelope, risk, data, API, and protected-semantic decisions as owner boundaries.
- **The agent could choose a large batch** -> Require the smallest dependency-valid slice reaching the earliest real boundary, then continue after proof rather than stopping for approval.
- **Static checks could mask weak runtime behavior** -> Use paired configured-session evidence and record model/source identities and raw action classification.
- **Long-session model sensitivity remains** -> Keep the rule near existing autonomy/ambiguity owners and align the completion arbiter as fallback; report this limitation honestly.
- **Route settling could create work after interruption** -> Pass the current audit abort signal through the finite wait and create no child/model call until readiness succeeds.
