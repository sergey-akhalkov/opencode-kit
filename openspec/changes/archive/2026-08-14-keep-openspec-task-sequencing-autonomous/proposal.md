## Why

An active OpenSpec apply session can still turn ordinary task ordering into an owner question when several implementation batches differ in size. The broad instruction to ask when ambiguity affects "scope" conflicts with the autonomy contract because it does not distinguish accepted outcome scope from orchestrator-owned sequencing.

## Outcome Capsule

- **Outcome**: OpenSpec apply selects and executes the next dependency-valid accepted task slice without asking the owner to choose a task range, batch size, or optional review detour.
- **Operating Envelope**: One already selected active change whose user-requested implementation scope is not explicitly bounded to a smaller task set; pending work remains local and inside existing action authority.
- **Non-Goals**: No automatic accepted-outcome expansion, no bypass of protected actions or explicit user limits, no task scheduler, and no permission/configuration change.
- **Non-Deferrable Invariants**: Owner questions remain mandatory for changed accepted semantics and exact protected decisions/actions; dependencies, safety gates, proof order, and user interruptions remain controlling.
- **Observable Proof**: A fresh configured OpenCode primary session given the reproduced multi-batch state selects the next focused dependency-valid slice and does not ask the owner; a paired protected-boundary scenario still stops at that exact boundary.
- **Material Residual Risks**: Model sensitivity and instruction-context competition cannot be eliminated by static markers; paired loaded behavior evidence is required.
- **Stop Line**: Stop when canonical/runtime surfaces, normative specs, focused contracts, paired loaded behavior proof, critical SDET, and applicable validation are complete. Unattended protected operations and generic project scheduling remain outside this change.

## What Changes

- Narrow material ambiguity from generic implementation "scope" to accepted outcome, operating envelope, risk, data, public API, and other protected semantics.
- Classify task order, task-range batching, implementation/reviewer choice, and current-cycle size as orchestrator-owned sequencing when the active change already defines accepted work.
- Require apply and completion arbitration to select the smallest dependency-valid next slice rather than present a routine owner menu.
- Settle transient hidden-arbiter route initialization before declaring a permanent capability mismatch, without issuing a model call during readiness checks.
- Add focused contract markers and paired same-model loaded behavior evidence while preserving exact owner boundaries.

## Capabilities

### New Capabilities

None.

### Modified Capabilities

- `library-instruction-artifacts`: Distinguish accepted-scope ambiguity from autonomous implementation sequencing on loaded instruction and completion-arbiter surfaces.
- `library-spec-workflow-integrity`: Require apply to choose the next dependency-valid accepted task slice without a routine task-range question.
- `session-completion-guard`: Bound provider-free hidden-arbiter route initialization before fail-closed capability classification.

## Impact

- Runtime instructions and guard route readiness: `global/AGENTS.md`, OpenSpec apply skill/command, completion arbiter, and session-completion-guard route/child owners.
- Normative OpenSpec requirements and focused instruction-contract tests.
- No application API, persisted data, provider/model route, permissions, install/activation, remote state, or release behavior changes.
