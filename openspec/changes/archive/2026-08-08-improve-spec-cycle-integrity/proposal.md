## Why

The kit has strong proof-first and proportional-delivery policy, but the default OpenSpec propose/apply/archive path does not enforce that policy, stale normative artifacts still pass validation, and the documented OpenCode config-loading model contradicts current runtime evidence. This creates false completion, avoidable re-planning cycles, hidden instruction sources, and persistent context and validation-output cost across projects.

## What Changes

- Add a portable Spec Capsule and artifact-specific OpenSpec rules so every current working increment identifies its outcome, enforced envelope, non-goals, non-deferrable invariants, observable proof, material residual risks, and stop line.
- Bind OpenSpec task completion and archive readiness to explicit evidence: edits alone do not complete a task, incomplete or unsynchronized changes do not archive as complete, and abandoned work uses an explicit non-completion disposition.
- Integrate cheap deterministic operation checks into the propose/apply/archive caller path instead of maintaining an unwired gate.
- Replace static active-roadmap claims with live OpenSpec discovery and synchronize canonical UDL, main specs, documentation, and structural drift checks.
- Correct `OPENCODE_CONFIG_DIR` documentation and diagnostics to reflect additive runtime loading and surface every loader-visible authority source without exposing private content.
- Make onboarding and `next-step` proportional: recommendation-only and serial by default, with planning fan-out, SDET, and optional review only when the request, risk, or project policy requires them.
- Narrow always-loaded context without broad safety deletion: move personal and machine-local facts to a schema-supported local instruction source and reduce only duplication that passes disposable workflow comparison.
- Separate deterministic structural validation from model-behavior evaluation, and keep process improvement subordinate to the accepted user outcome.
- Make every compaction evaluate a compact `three directions x two targets` improvement matrix: quality, cycle speed, and token economy for both the active working repository and `opencode-kit`. Each cell records observed evidence, the smallest cheap improvement, expected benefit, cost/risk, or `none` when the session provides no evidence.
- At next-session start, verify the matrix against the original user goal and execute at most one highest-ROI working-repository improvement when it is directly goal-linked, local, reversible, and in scope. Keep kit improvements separately visible; do not make kit work the next action while another repository goal is incomplete unless the kit defect directly blocks that goal or the owner explicitly included kit work in scope.
- Support faster, lower-noise iteration through focused checks during implementation, one complete freeze validation, concise green output, and measured rather than assumed test concurrency.

### Outcome Capsule

- **Outcome**: OpenSpec changes created and applied through the kit are bounded, implementation-ready, evidence-bound, and cheaper to iterate without weakening quality or protected-boundary safety.
- **Operating Envelope**: repository-local OpenSpec `spec-driven` workflows, OpenCode config/rule loading supported by the current official schema and observed local runtime, local non-destructive validation, and project adapters with concrete or reasoned non-applicable commands.
- **Non-Goals**: redesigning the OpenSpec CLI; introducing a new lifecycle profile; making optional reviewers mandatory; broad removal of the always-loaded safety floor; forcing parallel tests; automatically mutating `opencode-kit` during unrelated incomplete project work; installing, activating, deploying, publishing, or mutating external/default-global state.
- **Non-Deferrable Invariants**: edits alone never satisfy task completion; archive never represents incomplete work as complete; runtime-loading claims match observed behavior; representative proof and protected-boundary authority are not weakened; structural validators do not score fuzzy instruction quality; unrelated working-tree changes remain untouched.
- **Observable Proof**: operation entrypoints exercise their matching deterministic checks; generated proposal instructions expose the Spec Capsule rules; apply/archive fixtures demonstrate evidence-before-checkbox and fail-closed completion; loader diagnostics enumerate additive source locations; focused and freeze validation paths emit concise, actionable results; compaction output covers all six improvement cells without inventing evidence and selects no more than one admissible next-session action.
- **Material Residual Risks**: model adherence to changed prompts requires a dedicated same-model baseline/candidate workflow; exact AGENTS precedence under additive custom/default directories requires isolated loader proof; test parallelism may regress reliability under resource contention; mandatory improvement analysis may itself add token and process cost unless the six-cell output stays compact and permits `none`.
- **Stop Line**: stop when the integrated happy path and current-scope safety invariants are proved, applicable validation is green, and remaining work is optional catalog/profile optimization, broader OpenSpec upstream integration, or unmeasured performance tuning.

## Capabilities

### New Capabilities

- `library-spec-workflow-integrity`: Defines portable Spec Capsule authoring, evidence-bound task completion, fail-closed archive semantics, live status discovery, and proportional spec-workflow routing.

### Modified Capabilities

- `library-instruction-artifacts`: Align canonical UDL semantics, context ownership, proportional onboarding/next-step behavior, structural-versus-behavioral evaluation boundaries, and outcome-subordinate process improvement.
- `library-config-portability`: Replace the exclusive `OPENCODE_CONFIG_DIR` model with observed additive loading semantics and machine-local instruction separation.
- `library-tools-architecture`: Integrate operation gates into caller paths and define focused, concise, measured validation behavior without deleting unique test oracles.

## Impact

- OpenSpec configuration, commands, generated skills, operation gates, main specs, project guide, and status documentation.
- Global and project instruction surfaces, onboarding docs, `next-step`, UDL drift checks, and machine-local config examples.
- Doctor/runtime diagnostics for resolved config and instruction sources.
- Test command orchestration and success/failure reporting; no dependency or public product API change is intended.
- Running OpenCode sessions will require a new process before changed global instructions or config are observed.
