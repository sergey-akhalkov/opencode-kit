## Why

OpenCode sessions repeatedly spend model attention, tool calls, and context on deterministic command sequences such as collecting Git candidate state, correlating several outputs, and assembling the same lifecycle evidence. The kit already encourages deterministic helpers, but it has no bounded mechanism that converts observed repeated workflow cost into one reusable automation improvement before a substantial OpenSpec change completes.

## Outcome Capsule

- **Outcome**: The loaded OpenCode workflow uses one portable read-only repository candidate snapshot instead of manually collecting the same Git facts, and every Material or otherwise explicitly automation-eligible OpenSpec change harvests one observed repeated deterministic sequence by reusing, extending, or minimally building a discoverable project-owned helper before complete archive.
- **Operating Envelope**: Kit-managed OpenCode main sessions, Git worktrees, repo-local spec-driven OpenSpec changes, the portable global operation-gate/archive entrypoints, and disposable matched consumer workflows. The automation-dividend requirement applies only when the proposal explicitly selects it or Material routing makes it required; Ordinary Small changes remain exempt unless their accepted outcome itself introduces repeated automation.
- **Non-Goals**: A general workflow engine, arbitrary command recording or replay, model-generated shell macros, semantic policy in helper code, automatic Git mutation, a new helper file for every change, retroactive repair of archived changes, mandatory final retrospectives, or commit, push, release, deployment, installation, and machine-local activation.
- **Non-Deferrable Invariants**: Repository inspection is read-only and preserves staged, unstaged, untracked, conflicting, and unrelated work; automation never infers semantic correctness, scope, priority, or owner authority; accepted product proof and validation remain independent hard gates; one automation dividend cannot compensate for a broken outcome or weaker safety; reusable helpers have explicit inputs/effects/output, bounded privacy-safe diagnostics, stable ordering, effect-free help, and current real-entrypoint proof; existing owners are reused or extended before a new CLI or mechanism is added.
- **Observable Proof**: Run the candidate snapshot through its actual portable entrypoint against clean, staged, unstaged, untracked, conflict, detached-HEAD, and missing-upstream disposable Git states and compare every reported fact with direct Git observations. Then run matched baseline/candidate OpenCode consumer workflows with identical model, profile, permissions, fixtures, and requested outcome; require equivalent output, proof, validation, safety, diagnostics, and cleanup, no friction-vector regression, and a strict reduction in total tool calls for the repeated Git-inspection scenario. Prove that an automation-required complete archive fails without a current dividend record and passes with a candidate-correlated reused, extended, or new helper proof, while an explicitly exempt Ordinary Small change remains proportional.
- **Material Residual Risks**: A mandatory dividend can become ceremony or incentivize low-value helpers; snapshot output can become too broad or stale for the decision at hand; loaded routing text can increase context; Git edge cases and platform process resolution can diverge; and existing active changes may overlap instruction, operation-gate, archive, validation, and consumer-proof owners.
- **Stop Line**: Finish when the portable snapshot contract, one bounded automation-dividend declaration/evidence contract, loaded routing, apply/archive behavior, operation-gate enforcement, focused fixtures, matched consumer improvement proof, documentation/inventory, and project-native validation are complete on one current candidate. Do not build a generic workflow recorder, infer automation candidates from transcripts in helper code, require speculative automation from Ordinary Small work, rewrite archived changes, or automate commit/push/remote effects.
- **Automation Dividend**: required - replace repeated manual Git candidate-state collection with the portable repository candidate snapshot and use it through the current change's real proof and final candidate inspection.

## Claim And Evidence Scope

- **Claim ID**: HRAW-001
- **Claim Class**: Bounded workflow-friction improvement across matched consumer workflows.
- **Population**: The maintained disposable Ordinary Small and OpenSpec-backed consumer scenarios plus the fixed repeated Git candidate-inspection scenario defined by this change.
- **Coverage Basis**: Three matched baseline/candidate samples per maintained consumer scenario and deterministic Git-state fixtures covering the declared snapshot states.
- **Production Path**: The installed kit's loaded main-session instructions, portable repository snapshot entrypoint, OpenSpec operation gate, and complete-archive helper.
- **Comparison Paths**: Baseline manual Git status/diff/log collection versus candidate snapshot use under otherwise identical scenario inputs and environment.
- **Environment**: The same Windows OpenCode version, configured model/profile, permissions, kit dependency identity, disposable repositories, and scenario manifest digest for both arms.
- **Real Oracle**: Exact repository-state equivalence, accepted outcome and safety equivalence, candidate-correlated archive enforcement, complete cleanup, no friction-vector regression, and at least one strict median `totalToolCallCount` reduction.
- **Unresolved Observations**: Other operating systems, unusually large repositories, submodule-heavy worktrees, alternate Git implementations, non-Git projects, and workflows outside the maintained scenarios remain unmeasured.
- **Maximum Claim**: The candidate reduces tool calls without weakening outcome or safety for the fixed maintained scenarios; it does not prove universal model behavior, universal token reduction, or improvement for every repository workflow.

## What Changes

- Add a portable deterministic repository candidate snapshot that gathers the bounded Git identity, worktree-state, changed-path, diff-summary, upstream, and recent-history facts repeatedly needed by agents, with compact machine-readable output and targeted-detail references rather than unbounded patch content.
- Add an explicit automation-dividend declaration for OpenSpec changes. Material and owner-selected eligible changes must identify one observed repeated deterministic sequence and satisfy it through `reuse`, `extend`, or `build-minimal`; Ordinary Small changes can remain explicitly exempt without a retrospective.
- **BREAKING** Make a missing or stale required automation dividend block complete archive while preserving the existing rule that optional reflection, speculative improvements, and final-history analysis do not become completion scope.
- Extend apply and archive routing so the dividend is completed at the first current consumer after recurrence is observed, not invented as unrelated cleanup after product completion.
- Extend deterministic operation checks, evidence correlation, validation, documentation, and matched consumer proof to enforce the contract without inferring workflow value or semantic correctness from prose.

## Capabilities

### New Capabilities

- `agent-workflow-automation`: Defines the portable repository candidate snapshot, automation-dividend eligibility and evidence contract, reuse-first harvesting, proportional exemptions, and bounded workflow-friction proof.

### Modified Capabilities

- `library-instruction-artifacts`: Replace the unconditional non-blocking workflow-improvement rule with a narrow explicit automation-dividend exception for eligible changes while retaining proportionality, deterministic-helper, context-budget, and no-retrospective controls.
- `library-spec-workflow-integrity`: Add automation-dividend declaration, apply timing, evidence correlation, and complete-archive behavior without allowing optional observations to expand unrelated product scope.
- `library-tools-architecture`: Extend the portable operation gate and workflow-tool ownership requirements for the snapshot entrypoint and deterministic automation-dividend checks.

## Impact

- Loaded global workflow authority and OpenSpec propose/apply/archive skill and command sources, plus synchronized generated or project-local mirrors where they remain maintained.
- Portable helpers under `global/bin/`, operation-gate/archive core behavior, repository adapters, explicit contracts, validators, focused tests, and proof inventories.
- OpenSpec proposal/task/evidence conventions for active eligible changes; archived changes and explicitly exempt Ordinary Small changes remain unchanged.
- Existing `library-consumer-outcome-regression` runner, reviewed scenario manifest, and friction evaluator are reused for matched behavior evidence rather than introducing another evaluation mechanism.
- No new package dependency, semantic scoring, public API, persisted product data, remote operation, commit, push, release, deployment, installation, or machine-local activation is included.
