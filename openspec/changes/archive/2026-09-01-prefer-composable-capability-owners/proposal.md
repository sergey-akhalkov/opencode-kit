## Why

The kit already prefers reuse, current-owner extension, and cohesive source, but an accepted case can still be appended to one large physical file because the current contract does not explicitly separate semantic ownership from source-file shape. This change makes composition from directly testable capabilities the default when current evidence exposes a real capability boundary, while preserving direct implementation for cohesive work.

## Outcome Capsule

- **Outcome**: Every installed kit primary session preserves one semantic owner for accepted behavior while reusing, extracting, or minimally building independently testable owner-local capabilities when current evidence exposes a distinct contract and oracle, then composes those capabilities through the owner and proves the parent integration separately.
- **Operating Envelope**: Loaded global main and Material implementation authority on the supported OpenCode runtime; human-written application, proof, workflow-tool, and adapter changes; current-repository, platform/dependency, explicitly configured cross-project, and bounded public-ecosystem discovery; direct main implementation and bounded production delegation; disposable project-neutral proof roots with no consumer-product mutation.
- **Non-Goals**: Refactoring existing consumer repositories, requiring one module per task or function, imposing line/file/count thresholds, maximizing reuse regardless of lifecycle cost, adding a capability registry or inventory service, creating a new skill/agent/Practice Owner, publishing shared packages, forcing public APIs, or replacing cohesive direct code with wrapper-only microfiles or speculative frameworks.
- **Non-Deferrable Invariants**: Accepted behavior has one current semantic owner; extraction removes or delegates the old path rather than creating duplicate ownership; reused code is source-verified against its actual contract and effects; direct capability proof never substitutes for parent integration proof; protected boundaries, safety, data integrity, authorization, cleanup, and claim ceilings remain unchanged; and no discovery result authorizes installation, copying, publication, or remote mutation.
- **Observable Proof**: Through the installed configured kit in unrelated disposable projects, exercise at least: reuse of a verified existing capability; extraction of one independently observable private capability from one continuing semantic owner; non-expansion of a file that mixes unrelated semantic owners; direct implementation of a cohesive owner-local case; rejection of a wrapper-only or duplicate sibling; selection between an established ecosystem candidate and build-minimal using contract and lifecycle evidence rather than popularity alone; delegated preservation of the selected boundary; and separate component and parent integration observations.
- **Material Residual Risks**: Model-owned boundary classification can over-split cohesive work, leave a real capability buried, mistake physical extraction for competing ownership, or select an unsuitable reusable dependency; direct component tests can encourage false integration claims; added always-loaded wording can increase context or conflict with current `extend` and leaf-first behavior; and instruction-only enforcement remains model- and scenario-sensitive.
- **Stop Line**: Finish one project-neutral semantic-owner/physical-capability contract, proportional reuse-extract-build decision behavior, direct capability proof plus parent integration proof, production-role continuity, focused deterministic drift checks, and installed behavior evidence. Stop before consumer-project refactors, a toolkit registry, package publication, dependency installation, a new planner/reviewer/skill, language-specific module rules, numeric architecture scoring, or universal modularity claims.
- **Delivery Horizon:** none - this is a universal kit workflow correction, not part of a declared product delivery horizon.

## What Changes

- Clarify that one semantic owner may be implemented by a thin coordinator plus private cohesive capability modules, and that owner reshape may extract such a module when the old path delegates and duplicate ownership is removed.
- Require a proportional composition decision before extending human-written code: remove or narrow, reuse a verified capability, directly extend a cohesive owner, or extract/build the smallest owner-local capability when a current independent contract and oracle justify it.
- Require directly exercisable capability evidence before parent composition where that boundary exists, while keeping parent integration evidence distinct and preserving direct behavior for inseparable cases.
- Treat established ecosystem use as a contract, provenance, maintenance, license/security, adaptation, and total-lifecycle-cost decision; popularity is evidence, not an automatic selection rule.
- Preserve current `architecture-and-change-locality`, `simplicity-and-reuse`, and leaf-first task ownership without adding a new runtime owner or a one-task/one-module mapping.
