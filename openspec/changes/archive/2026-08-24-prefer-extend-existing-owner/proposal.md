## Why

Loaded reuse guidance fires on new mechanisms and after-the-fact duplicates, while Ordinary Small and production roles treat reshaping a current owner as an unrelated refactor. Agents therefore add sibling files for accepted new cases of an existing responsibility. The always-loaded reuse paragraph is already at the committed startup ceiling, so the default must be replaced, not appended.

## Outcome Capsule

- **Outcome**: When an accepted new feature is a new case of a current same-responsibility owner, main names that owner and defaults to `extend` (reshape the owner so the feature is a case, not a sibling implementation). `code-quality-reviewer` remains the `simplicity-and-reuse` Practice Owner and observes only an explicit sibling or same-versus-new uncertainty. Trivial owner-local work stays ceremony-free.
- **Operating Envelope**: Loaded OpenCode main-session and production-role guidance for Ordinary Small and Material work in the current repository. Applies only when the accepted increment adds behavior that already has a current same-responsibility owner, or when the author is about to add a second implementation of that owner. Owner-local fixes, data/config/generated/mechanical edits, and glue under an already selected API remain exempt unless they independently add a sibling or new mechanism.
- **Non-Goals**: A new Practice Owner or agent; mandatory reviewer launch on every feature; written disposition for punctuation or selected-API glue; inverting Rule of Three into always-extract; reviewer authority to authorize or mutate; merging `architecture-and-change-locality` with `simplicity-and-reuse`; collapsing `tools/proofs` clones into `lib/`; raising the committed startup token-proxy maximum; changing product, public API, persisted-data, or remote behavior.
- **Non-Deferrable Invariants**: Main remains the applicator and result owner. The Practice Owner stays read-only and non-authorizing. `extend` means reshape the current owner; `build-minimal` remains only for a genuinely new responsibility. Architecture still owns mixed-file / new-responsibility / seam decisions. AHA, YAGNI, and Rule of Three still forbid hypothetical shared frameworks. Combined `principles-of-work.md` plus `global/AGENTS.md` token proxy stays at or below 13,279 by replacement, not growth. Zero-trigger Ordinary Small launches no owner.
- **Observable Proof**: Extend the existing `reuse-discovery` disposable authoring proof with one `extend-existing-owner` scenario and keep the current `local-owner` and `trivial-fix` controls. Same model, profile, permissions, and cleanup envelope. Retain the candidate only when the new scenario records `extend` against the named current owner without a sibling module, the triggered mechanism scenario still loads reuse detail, the trivial scenario loads no reuse skill and launches no owner, and committed startup authority does not grow.
- **Material Residual Risks**: Same-versus-new responsibility remains a judgment call and can be misclassified as architecture work or as a new mechanism; one synthetic scenario cannot prove all languages or repositories; replacing always-loaded text can drop a protected reuse or safety marker; a wider owner trigger can leak into Ordinary Small if worded as "any new file".
- **Stop Line**: Finish when the compact always-loaded rule, `extend` definition, production-role reshape clarification, Practice Owner sibling/uncertainty triggers, one new proof scenario, deterministic marker/budget checks, and matched baseline/candidate evaluation are green on one candidate. Do not add an owner, raise the budget, collapse proof-harness clones, or require a reviewer on every feature.
- **Automation Dividend**: required - extend `tools/proofs/reuse-discovery.ts` with one `extend-existing-owner` scenario and reuse its existing preflight/capture/evaluate owner instead of adding a runner.

## What Changes

- Replace the always-loaded reuse paragraph so that before a new file, module, or function for accepted behavior, main names the current same-responsibility owner or records `no-current-owner`, and defaults to `extend` when an owner exists.
- Define `extend` as reshaping that owner's contract or shape so the accepted feature becomes a case of the same owner, not a sibling implementation.
- Keep `reuse-discovery` as the lazy detail owner for search order and `reuse | extend | build-minimal`. Load it for a new mechanism, an explicit sibling, or same-versus-new uncertainty; do not load it for owner-local fixes or selected-API glue.
- Narrow the `simplicity-and-reuse` runtime triggers to an explicit sibling implementation of a live owner, plus named uncertainty when same-versus-new responsibility is decision-changing. Do not launch on every feature.
- Clarify in production roles that "unrelated refactor" does not include reshaping the current owner to absorb an accepted new case inside the write scope.
- Add one `extend-existing-owner` scenario to the existing reuse-discovery proof. Do not collapse `tools/proofs/lib` in this increment.
- Pay for always-loaded words by consolidating the current reuse paragraph. Do not raise the 13,279 token-proxy maximum.
