## Context

See `proposal.md` for motivation. The current control surface has four relevant facts:

1. `global/principles-of-work.md` already says to trust but verify and to use the
   smallest safe test that can disprove an explanation, but it does not operationally
   apply that stance to a just-authored result before confidence is claimed.
2. `/opsx-propose` builds artifacts and runs deterministic operation gates plus strict
   OpenSpec validation. Those checks prove structure and explicit fields, not that the
   authored framing solves the original request.
3. `implementation-readiness-reviewer` already owns stable scope, unresolved decisions,
   observable requirements, and proof boundaries. Its trigger currently fires when those
   facts are visibly unresolved, not when one author has just declared them resolved.
4. `add-foundation-integrity-autorecovery` proposes a separate later bind/rebind
   contradiction owner. `add-continuous-complexity-management` and autonomous audit work
   own different pre-expansion and exhaustive-review concerns. This change must not
   duplicate those roles or race their active shared paths.

The observed planning history in
`add-continuous-complexity-management/planning-review-disposition.md` also demonstrates
the failure and the opposite excess: fresh reviews found real ownership, profile,
failure-model, and claim inconsistencies, but multiple specialist rounds created a large
review surface. The required mechanism therefore optimizes for one high-signal challenge,
not maximal reviewer coverage.

## Goals / Non-Goals

**Goals:**

- Improve the first candidate by forcing original-request, success-oracle, failure, and
  unnecessary-scope reasoning before artifacts are drafted.
- Obtain one genuinely fresh attempt to falsify task fit at the earliest high-leverage
  decision boundary.
- Reuse existing review owners and proof infrastructure.
- Persist enough candidate-correlated evidence for a later apply session to avoid both
  blind trust and duplicate review.
- Make no-finding a valid terminal result and enforce one initial plus at most one
  materially justified re-review.
- Preserve exact Practice Owner routing, critical SDET, structural validation, and main's
  sole outcome/mutation authority.

**Non-Goals:**

- Prove that a model can always create or recognize a correct plan.
- Add a new reviewer agent, review orchestrator, semantic quality score, or universal
  every-task gate.
- Replace exhaustive audit, code review, architecture review, claim challenge,
  foundation-integrity recovery, or critical SDET.
- Persist raw private conversation text, chain-of-thought, or a global cross-project
  review ledger.
- Add a third generic challenge because a reviewer or author wants more confidence.

## Decisions

### 1. Extend outcome readiness instead of adding a universal critic

The current owner is `implementation-readiness-reviewer`; select `extend`. Add
original-request task fit, unnecessary scope, late-decision surprise, explicit
falsification attempts, and `no-material-finding` to that role. Expand the reviewed
`outcome-readiness` trigger to include a just-authored decision-material artifact before
semantic implementation readiness.

This remains one responsibility: can a cold implementer build and prove the accepted
increment without solving the wrong problem or guessing a material decision? The role
does not become a product decider, architecture owner, claim reviewer, final approver, or
generic code reviewer.

For a Material request without a formal plan, main creates the smallest decision frame
containing the original request, current decision surface, envelope, proof boundary, and
failure hypotheses, then uses the same readiness owner before production mutation. This
frame may live in the current project-native planning surface or the session handoff; it
does not require inventing OpenSpec. `final-candidate-reviewer` remains optional under its
existing post-proof concrete-risk trigger and never becomes the generic fallback.

Alternatives rejected:

- A new `adversarial-reviewer` would overlap outcome readiness, create another discovery
  surface, and invite broad every-task use.
- Extending `foundation-integrity-reviewer` would mix initial task-fit authoring with
  later cross-identity bind/rebind invalidation; its active proposal explicitly keeps
  generic quality and task-size triggers out.
- Main-only self-review would retain the same authored framing and would not reproduce
  the fresh-context property the user observed.
- A fixed sequence of readiness, architecture, instruction, claim, and code-quality
  reviewers would repeat the high-cost pattern rather than create one bounded challenge.

Reuse disposition:

- **Requested capability and trigger:** fresh semantic task-fit challenge for
  decision-material authored results; same-versus-new uncertainty.
- **Sources reached:** current readiness/final/architecture/instruction/claim reviewer
  contracts, Practice Ownership, propose/apply gates, consumer-outcome proof harness, and
  active overlapping changes.
- **Material candidates:** extend `implementation-readiness-reviewer` for formal and
  inline Material decision frames; leave `final-candidate-reviewer` optional; reject a
  new agent.
- **Disposition:** `extend`.
- **Reason:** existing readiness ownership fits the pre-investment contract at lower
  discovery, maintenance, profile, permission, and proof cost than a sibling role.
- **Cross-project:** `not-applicable` because this is a portable kit routing change and no
  external implementation candidate is needed.

### 2. Use a semantic decision-material trigger, not size heuristics

A result is decision-material when it resolves or assumes a fact capable of changing at
least one current item:

- accepted outcome;
- technically enforced operating envelope;
- non-deferrable invariant;
- observable proof boundary;
- user-owned product or protected decision;
- material residual risk.

Plans, specifications, and architecture artifacts matching that predicate receive the
early challenge. Material work without a formal planning artifact first receives the
minimal decision frame and the same early challenge.
An exact owner-local reversible Ordinary Small change with known behavior and validation
is exempt. Material work cannot bypass the early boundary merely because no durable plan
exists; it receives the minimal decision frame first.

OpenSpec proposals add exactly one reviewed declaration:

```text
Bounded Falsification Review: required - <decision surface>
```

or:

```text
Bounded Falsification Review: exempt - <Ordinary Small reason>
```

The declaration is semantic seed data authored by main. The operation gate validates
only uniqueness and shape. It must not infer Material, count tasks, scan for risk words,
or approve the reason.

Alternatives rejected:

- Requiring review for every OpenSpec change would turn Ordinary Small into ceremony.
- Task/file/line thresholds are easy to game and do not correlate reliably with decision
  consequence.
- Leaving the trigger entirely implicit would make later apply sessions unable to tell a
  reviewed exemption from an accidentally skipped challenge.

### 3. Improve first-pass authoring before dispatching a critic

For a required episode, main first creates a compact private working frame from the
original request, not from the proposed artifact:

```text
Original accepted request
  -> observable success boundary
  -> current envelope and non-goals
  -> strongest realistic wrong-task path
  -> strongest hidden-decision path
  -> strongest late-implementation invalidation path
  -> strongest unnecessary-work candidate
  -> first artifact candidate
```

Only decision-relevant outcomes belong in durable artifacts. Do not persist hidden
reasoning or raw conversation text. The durable review record references a privacy-safe
request event/session reference or an accepted outcome capsule, while the fresh child
brief receives the original request text under the current session's privacy boundary.

This author-side inversion is not accepted as independent evidence. It exists to improve
the first candidate and reduce the correction rate before the fresh challenge.

Alternative rejected: writing the candidate first and then asking the same context
whether it looks complete preserves anchoring and spends the challenge only after avoidable
defects have already entered every dependent artifact.

### 4. Give the fresh child a falsification brief, not a request to find issues

The challenge brief includes:

- original accepted request and success boundary as a separate input;
- candidate reference and all apply-required artifact paths;
- operating envelope, non-goals, non-deferrable invariants, and material risks;
- current source/evidence references that can disprove artifact assumptions;
- six attack classes: coherent-but-wrong outcome, silent user-owned decision, missing
  observable oracle, late implementation invalidation, internal contradiction, and
  unnecessary scope;
- finding-admission fields and the explicit permission to return
  `no-material-finding`;
- read-only, no-question, no-nested-agent, no-mutation, and no-lifecycle-authority
  boundaries.

The reviewer reports attempted attack classes as well as admitted rows. This reduces the
pressure to fill a risk matrix merely because a matrix exists. It does not require prose
for every failed hypothesis; a compact terminal class row is enough.

Alternative rejected: “audit this thoroughly and find significant problems” makes a
non-empty finding set an implicit success criterion and encourages scope invention.

### 5. Persist one compact project-native episode record

For required OpenSpec changes, main writes `falsification-review.md` beside the planning
artifacts. It is not an additional schema dependency that authors must design manually;
the propose/apply surfaces own it as evidence. The compact record contains:

```text
Original Request Ref
Accepted Outcome Ref
Candidate Ref
Decision Surface
Reviewer Session Ref
Effective Model
Challenge Count: 1 | 2
Attack Classes: terminal status per class
Material Findings: stable ids or none
Main Dispositions: confirmed | falsified | unreachable | unknown | owner-boundary
Correction Ref / Invalidated Surface
Terminal Reason
Unresolved Evidence
```

For exempt OpenSpec changes, the proposal declaration is sufficient; no empty review
file is created. For non-OpenSpec repositories, use the existing project-native planning
or handoff surface. Do not invent an OpenSpec tree solely for this record.

The record stores references and dispositions, not full reviewer transcripts or raw user
messages. Existing evidence retention can preserve a longer report when independently
needed by Material qualification.

Alternatives rejected:

- Transcript-only evidence disappears from a cold apply session and causes duplicate
  review or blind trust.
- Adding the reviewer report itself as a mandatory OpenSpec schema artifact would make
  model prose part of structural readiness and increase every change's authoring burden.
- Reusing `history.md` would misclassify no-finding review evidence as an attempted
  strategy and overload its causally distinct strategy purpose.

### 6. Admit only material, current, evidence-backed findings

An admitted row needs all of:

1. accepted outcome or non-deferrable invariant at risk;
2. reachable scenario in the current enforced envelope;
3. concrete consequence;
4. exact artifact, source, or live evidence;
5. current-scope justification;
6. smallest sufficient correction.

Main independently checks the row. `confirmed` authorizes only the smallest correction
already required by the accepted outcome. `falsified`, `unreachable`, optional,
future-scope, style, and polish produce no task or review continuation. `unknown` narrows
semantic readiness only when the missing fact can materially affect the current outcome;
otherwise it remains a residual limitation.

No-finding is a first-class terminal state. Neither the reviewer nor main receives a
target finding count, quality score, confidence quota, or requirement to propose an
improvement.

### 7. Bound invalidation and terminate after at most two generic challenges

The episode state machine is:

```text
required
  -> challenged -> no-material-finding -> closed
  -> challenged -> all-rows-falsified/parked -> closed
  -> challenged -> confirmed -> corrected
       -> correction-does-not-change-challenged-surface -> focused-proof -> closed
       -> correction-changes-challenged-surface -> re-reviewed -> closed
  -> reviewer-unavailable/unusable -> unknown
```

The initial challenge count is one. A correction that changes outcome, envelope,
invariant, proof boundary, user-owned decision, or material-risk surface permits one
fresh re-review. The re-review exhausts the generic budget even if it finds another
material defect. Main still corrects a reproduced defect, but closes it through focused
proof or the exact registered Practice Owner rather than asking a third generic reviewer
for another verdict.

An unchanged candidate/request/evidence tuple reuses its terminal record. A new accepted
user requirement is a new episode because it changes the goal, not because the author
wants another attempt. Attempt limits remain revisable controls if evidence invalidates
this exact design, but changing the limit during implementation cannot manufacture
authority for review, mutation, or protected action.

Alternative rejected: “repeat until no findings” has no stable stopping oracle because a
model can always invent another preference, future variant, or reformulation.

### 8. Separate structural artifact readiness from semantic readiness

`/opsx-propose` keeps the current sequence for scaffold, artifact generation, operation
gate, and strict validation. Its user-facing status becomes two facts:

```text
Structural artifact readiness: passed | failed
Bounded falsification: exempt | no-material-finding | corrected-and-closed | unknown
Semantic implementation readiness: ready | unknown
```

Only a reviewed exemption or current closed required episode permits `ready`. A missing
review does not make OpenSpec validation red; it makes the broader readiness statement
unknown. `/opsx-apply` reads the declaration and current record before substantial work,
does not repeat a closed episode, and invalidates only materially changed challenged
surfaces.

This narrows the current overloaded `Ready for implementation` phrase without weakening
the deterministic gates or pretending they perform semantic review.

### 9. Prove behavior with a reviewed configured partition pack

Extend the existing consumer-outcome configured-session harness; add no new proof runner.
Use the exact proposal population ids:

1. `coherent-wrong-outcome`
2. `silent-owner-decision`
3. `missing-observable-oracle`
4. `late-implementation-surprise`
5. `unnecessary-scope`
6. `clean-no-finding`
7. `material-correction-rereview`
8. `unchanged-repeat`
9. `optional-polish`
10. `ordinary-small-exempt`
11. `exact-practice-owner`
12. `material-inline-plan`

The frozen pre-product observations retain their original request, actor-visible shared
fixture, model/variant, profile, permissions, environment, and output bounds. Current
candidate captures use actor-visible member-local fixtures so one member cannot be
invalidated or influenced by an unrelated case row. Reviewed scenario records own the
semantic inputs, correction surface, and expected terminal facts; the fresh reviewer does
not receive the expected disposition row. Deterministic code validates input identity,
session freshness, tool/role attribution, count no greater than two, terminal state,
artifact references, privacy, and cleanup. It does not decide whether prose is a real
finding or rewrite an observed row into the expected row.

The frozen and current lanes are compared directly only when request and every relevant
environment/initial-state identity match. A runner correction that changes actor-visible
fixture bytes creates a separately identified candidate-establishment lane; historical
baseline characterization remains useful but cannot support a causal improvement or
substitution claim. This keeps a truthful narrower candidate behavior result instead of
waiving an environment mismatch or repeating an unavailable pre-product source.

The first real boundary is one configured `coherent-wrong-outcome` scenario through the
existing build runner and loaded main bounded-episode routing used by propose. Its
member-local seed contains `case.json`, a mutable `candidate.md`, and a discoverable
reviewed record contract. The root supplies the original request to one fresh child
without the expected disposition, independently reproduces any admitted row, corrects
`candidate.md`, and writes the terminal record before semantic readiness. This slice does
not claim literal `/opsx-propose` command execution because its exact permission envelope
denies the command's broader skill/bash/OpenSpec scaffold. Do not build the remaining
population before this complete candidate path works.

The change-level claim remains `unknown` until actual configured observations and a
fresh evidence-sufficiency challenge exist. Planning review cannot substitute for this
runtime population closure.

### 10. Serialize active instruction and proof ownership before implementation

This change is planning-only now, but later implementation touches likely shared surfaces
with active changes:

- `global/AGENTS.md`, `global/principles-of-work.md`, reviewer contracts, and instruction
  context-quality controls;
- Practice Ownership seed/view/tests;
- OpenSpec propose/apply command and skill mirrors;
- consumer-outcome fixtures/evaluator and capability specs.

The first implementation task must refresh active-change ownership and establish an
acyclic dependency, serial order, isolated path, or explicit ownership transfer for every
shared file. `replace-instruction-limits-with-context-quality` must apply first, or this
change must explicitly rebase before mutation. In particular,
`add-foundation-integrity-autorecovery` may add a new owner and
change the same registry/profile surfaces; this change must extend its resulting roster
rather than overwrite or parallel-edit it. `add-continuous-complexity-management` may
change instruction/proof surfaces and must receive the same treatment.

## Risks / Trade-offs

- [The fresh reviewer manufactures defects because it expects findings] -> Make
  no-finding terminal, require complete admission evidence, record failed attack classes,
  and give no finding-count or novelty objective.
- [Decision-material becomes an every-task synonym] -> Tie it only to six consequence
  surfaces, retain explicit Ordinary Small exemption, and prove negative controls.
- [One reviewer misses a domain-specific defect] -> Keep exact Practice Owner triggers;
  the generic episode tests task fit and does not claim domain completeness.
- [Two-review ceiling leaves a corrected second finding without another generic verdict]
  -> Require focused proof or exact-owner evidence for the affected boundary; generic
  confidence seeking is not the oracle.
- [Persistent review records add process weight] -> Create one compact file only for
  required OpenSpec episodes, store references rather than transcripts, and create no file
  for exemptions.
- [Original user request contains sensitive content] -> Pass it only inside the current
  bounded session/child brief and persist a privacy-safe reference plus accepted outcome,
  not raw private text.
- [Unavailable reviewer blocks useful work] -> Preserve structural readiness separately
  and semantic readiness as `unknown`; Ordinary Small remains unblocked. Do not fake
  independent evidence.
- [Instruction growth duplicates authority or weakens behavior] -> Consolidate only
  evidenced overlap, keep detailed procedure on demand, report inventory diagnostics,
  and require canonical ownership, exact-duplicate, context-quality, and loaded behavior
  evidence. Diagnostic size growth alone is not a failure.
- [Active changes race on shared files] -> Make path-level ownership/dependency closure
  the first task and prohibit mutation until it is current.

## Migration Plan

1. Apply the instruction-context replacement contract, then refresh current active-change
   ownership, installed source identity, instruction diagnostics, and context-quality
   status; serialize or transfer every shared implementation path.
2. Freeze matched baseline fixture records and current source before behavior changes.
3. Add the capability record/declaration schema and provider-free negative fixtures.
4. Extend readiness/final reviewer contracts and compact global routing by replacing
   overlapping wording rather than appending a second philosophy.
5. Integrate propose/apply declaration, episode record, status wording, and structural
   gates as one coherent slice.
6. Run the one-scenario configured real boundary, then complete the reviewed partition
   pack and provider-free replays.
7. Run exact Practice Owner maintenance review, main disposition, instruction/profile/
   OpenSpec validation, and the fresh broad-claim evidence challenge.
8. Installation or activation remains a separate maintainer action. Running OpenCode
   sessions require restart before changed config-time artifacts are observed.

Rollback is the scoped source/profile/command/proof diff plus generated readback. Review
records created only in disposable proof projects are removed after terminal process and
session closure; immutable privacy-safe evidence bundles remain available for replay.
