# Strategy History

## 2026-08-26 - Extend Outcome Readiness Or Claim Evidence

- **Objective:** Close the wrong-foundation recurrence without adding another core Practice Owner.
- **Approach:** Put workload/profile/environment/oracle comparison into either `implementation-readiness-reviewer` or `evidence-sufficiency-reviewer` and reuse its current launch trigger.
- **Evidence:** Current contracts route outcome readiness when the outcome/envelope/first boundary is unresolved and claim evidence only for declared broad claims. The recurrence can arise after readiness and before a broad claim, while locally green implementation and proof continue accumulating. The instruction-governance and architecture planning reviews independently identified the cross-identity foundation relation as a distinct responsibility.
- **Outcome:** Rejected for this change.
- **Reason:** Either extension would miss part of the reachable event window and give one owner two independent change axes; it would also make broad-claim declaration a prerequisite for early foundation detection.
- **Do Not Repeat Until:** Current owner contracts or matched runtime evidence show the foundation relation is always and uniquely reached by one existing trigger without widening Ordinary Small review.
- **Evidence-Based Retry Condition:** A maintained scenario proves the distinct owner adds no decision-changing observation while one existing owner reliably detects the same bind/rebind contradiction earlier with lower total routing cost and no overlap.

## 2026-08-26 - Add A Semantic Plugin, Score, Or Foundation Database

- **Objective:** Make detection deterministic and persistent across sessions and projects.
- **Approach:** Add a provider plugin or helper that extracts identities from repository text, scores mismatch likelihood, stores project foundation records, and launches recovery above a threshold.
- **Evidence:** Workload, profile, configuration, environment, and oracle meaning is project-domain semantics rather than a stable textual shape. Existing deterministic-automation rules forbid model-like inference, ranking, or scoring in helpers, and project memory is advisory rather than normative authority. The accepted increment needs one current relation and bounded local recovery, not a new storage lifecycle.
- **Outcome:** Rejected.
- **Reason:** It would turn heuristic output into product authority, add migration/privacy/staleness responsibilities, and still require semantic model review and main disposition.
- **Do Not Repeat Until:** A reviewed cross-domain schema and authority model exists independently of this change and deterministic extraction has direct source-backed correctness evidence.
- **Evidence-Based Retry Condition:** At least three maintained independent consumers expose the same explicit machine-readable relation contract, and a deterministic parser can validate it without text inference, scoring, project-memory authority, or new protected decisions.

## 2026-08-26 - Combine Detection And Recovery In One Agent

- **Objective:** Minimize handoffs by letting one specialist detect, plan, edit, sweep, and approve the corrected foundation.
- **Approach:** Create a mutation-capable foundation agent with repository-wide planning authority and make its terminal report the recovery decision.
- **Evidence:** Practice Owners are read-only and non-authorizing; main is the sole outcome, mutation, integration, proof, and owner-question authority. A combined agent would use its own finding to authorize its writes, introduce another orchestrator and concurrent-writer lifecycle, and make one context both author and reviewer.
- **Outcome:** Rejected.
- **Reason:** The apparent handoff saving weakens evidence-not-authority, writer safety, and independent corrected-candidate review.
- **Do Not Repeat Until:** The user explicitly transfers outcome authority and the runtime supplies isolated writer ownership plus an independent post-write review boundary.
- **Evidence-Based Retry Condition:** Repeated matched evidence shows main-owned recovery is the causal bottleneck and a bounded mutation agent can reduce it without self-authorization, overlapping writes, lost context, or Ordinary Small overhead.

## 2026-08-26 - Put The Complete Loop In Always-Loaded Routing

- **Objective:** Ensure every main session remembers every foundation identity, recovery step, sweep classification, and anti-loop condition.
- **Approach:** Append the full relation model, incident state machine, propagation algorithm, and evidence rules to `global/AGENTS.md` and run the review on every task.
- **Evidence:** The core startup budget is already 11,999 of 12,000 token-proxy units, Ordinary Small zero-trigger behavior is a maintained invariant, and existing Practice Ownership uses compact descriptions with detailed bodies on demand. The full loop is relevant only after a named bind/rebind event and, for recovery, after main confirmation.
- **Outcome:** Rejected.
- **Reason:** It would breach the startup ceiling, duplicate on-demand contracts, and convert a material event trigger into universal ceremony and polishing pressure.
- **Do Not Repeat Until:** A separate owner-authorized budget or routing model changes and matched evidence shows compact discovery cannot select the owner reliably.
- **Evidence-Based Retry Condition:** Candidate captures repeatedly miss the exact material trigger after description/compact-routing corrections, while an equivalent replacement (not append) demonstrably fixes those cases without regressing Ordinary Small or other owners.

## 2026-08-26 - Wait For Owner Approval Before Corrective Planning

- **Objective:** Avoid autonomous correction of a wrong product foundation.
- **Approach:** After every confirmed mismatch, stop for owner approval of the correction, new OpenSpec change, task updates, and active-change sweep, optionally with a fixed waiting period.
- **Evidence:** The user explicitly requires autonomous recovery after confirmation. Existing authority already permits main to update planning controls and dependency closure when accepted semantics remain unchanged; protected product/API/data/security/legal choices remain separately owner-bound. A fixed wait does not add evidence or safety when one correction is uniquely determined.
- **Outcome:** Rejected.
- **Reason:** It adds an unnecessary owner hop, leaves known wrong-foundation work active, and confuses process approval with protected semantic authority.
- **Do Not Repeat Until:** The accepted outcome changes to require owner approval for local corrective planning or evidence shows unique-correction classification cannot preserve protected boundaries.
- **Evidence-Based Retry Condition:** A reproduced scenario shows autonomous recovery selected among genuinely ambiguous protected product identities despite the falsification and owner-boundary guards; then narrow only that decision boundary.

## 2026-08-26 - Add A Separate Foundation Proof Runner

- **Objective:** Prove owner launch, local mutation, dependency sweep, archive preservation, and anti-loop behavior in one purpose-built executable.
- **Approach:** Create a new configured-session CLI and evaluator beside the existing Practice Owner and consumer-outcome runners.
- **Evidence:** `practice-owner-routing.ts` is intentionally read-only and cannot prove recovery mutation, while the existing consumer-outcome harness already owns configured-model source staging, pack contracts, local write containment, baseline/candidate comparison, immutable bundles, evaluator replay, privacy, session cleanup, and filesystem readback.
- **Outcome:** Rejected in favor of extending the current consumer-outcome owner.
- **Reason:** A new runner would duplicate the most failure-prone capture/evaluator/cleanup machinery; weakening the read-only routing runner would violate its current boundary.
- **Do Not Repeat Until:** The existing consumer-outcome pack contract cannot express exact owner attribution plus contained planning mutations without weakening another maintained pack.
- **Evidence-Based Retry Condition:** Provider-free preflight demonstrates an irreducible contract or permission conflict in the existing harness and a narrow shared-library extension cannot resolve it.

## 2026-08-26 - Distinct Read-Only Owner Plus Main-Owned Recovery

- **Objective:** Detect a current material foundation contradiction early, correct only its dependent current work autonomously, and terminate without polishing or recursive incidents.
- **Approach:** Add one core `foundation-integrity-reviewer`, one on-demand main-executed recovery skill, compact bind/rebind routing, one project-native incident episode, serial dependency-scoped propagation, immutable-history narrowing, unchanged budget ceilings, and one extended configured-session partition pack.
- **Evidence:** Current registry/profile/proof owners provide the structural and runtime substrate but no current owner covers this relation. Independent instruction-governance and architecture reviews supported the detect-versus-recover split. Current budget measurement proves new bodies require duplicate removal rather than limit growth. The pmac recurrence supplies the positive generalized case, while existing zero-trigger and evidence-not-authority contracts supply negative and safety controls.
- **Outcome:** Selected for proposal, specifications, design, and implementation tasks.
- **Reason:** It is the smallest coherent architecture that changes the reachable behavior while preserving main authority, current owners, unrelated work, archives, proportional routing, and deterministic-helper boundaries.
- **Do Not Repeat Until:** N/A - selected strategy.
- **Evidence-Based Retry Condition:** Provider-free validation or matched baseline/candidate evidence disproves a specific selected boundary; revise only that boundary and retain all unaffected proof rather than returning to a rejected broad mechanism.
