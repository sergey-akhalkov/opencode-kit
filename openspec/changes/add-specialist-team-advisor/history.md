# Strategy History

## Strategy 1: Add More Main-Session Checklists And Compaction Reminders

- **Objective:** Prevent main from forgetting relevant specialist agents during long work.
- **Approach:** Consider regular all-agent checklists, done-done review, and generic post-compaction reminders.
- **Evidence:** Current main already retains outcome, safety, proof, worktree, routing, implementation, and integration obligations. Maintained `CLC-001` evidence shows two missed architecture-owner launches despite loaded routing rules, while another owner-routing scenario over-launched protocol and wire owners. Generic reminders would add context without preserving a detected task-specific obligation.
- **Outcome:** Rejected for the current increment.
- **Reason:** It increases the same main cognitive load, detects omissions late, and encourages ceremony or over-routing without transferring team-topology work.
- **Do-Not-Repeat Condition:** Do not add an all-agent checklist, fixed reviewer sequence, launch-count target, or vague `remember specialists` compaction text.
- **Evidence-Based Retry Condition:** Reconsider only if future runtime evidence shows that a bounded task-specific advisor cannot operate while a smaller explicit checklist measurably fixes the same maintained missed/extra-routing scenarios without context or latency regression.

## Strategy 2: Use A Routing Skill Without A Fresh Advisor

- **Objective:** Reduce routing latency by injecting a specialist-selection procedure directly into main.
- **Approach:** Add one skill that makes main classify the task, inspect available roles, and form its own team.
- **Evidence:** Skills are appropriate for procedural memory but execute inside the same main context. The accepted problem is that main simultaneously owns mission state, implementation, proof, and routing; skill-only routing leaves that high-load semantic decision and initial anchoring unchanged.
- **Outcome:** Rejected as the semantic team-selection owner.
- **Reason:** It structures main's work but does not independently challenge or remove the routing decision from main. A parallel skill would also duplicate advisor triggers and engagement-map semantics.
- **Do-Not-Repeat Condition:** Do not add a routing skill that repeats catalog interpretation, team selection, or reconsultation logic.
- **Evidence-Based Retry Condition:** Reconsider only if matched evidence shows a thin non-semantic packaging skill removes measurable context or latency without duplicating advisor behavior or restoring team selection to main.

## Strategy 3: Extend An Existing Readiness Or Generic Helper Agent

- **Objective:** Avoid adding a new agent by reusing `implementation-readiness-reviewer` or `qwen-local-worker`.
- **Approach:** Consider a team-routing mode on the readiness owner or generic first-pass routing by the helper.
- **Evidence:** `implementation-readiness-reviewer` already owns the registered `outcome-readiness` practice and is the selected challenger for active bounded-falsification work. `qwen-local-worker` is a generic first-pass helper, has no root-team contract, and is absent from default `core`. Team topology covers default non-trivial root missions, mid-task changes, skills, Practice Owners, workers, and conditional timing.
- **Outcome:** Rejected; choose one dedicated non-owning advisor.
- **Reason:** Extending either live role would mix responsibilities, create trigger overlap, or make default availability depend on an optional helper profile.
- **Do-Not-Repeat Condition:** Do not add a readiness-reviewer team mode, promote qwen helper to router, or retain two semantic advisors.
- **Evidence-Based Retry Condition:** Reconsider only if current role ownership changes independently and matched behavior proves one existing cohesive role satisfies every maintained team-advice scenario with lower total context and no practice/helper regression.

## Strategy 4: Dedicated Advisor With An Auto-Discovered Global Plugin

- **Objective:** Give a fresh advisor the actual root-effective agent and skill catalog without asking main to copy a static roster.
- **Approach:** Add `specialist-team-advisor` and initially place `specialist-catalog.ts` under `global/plugin/`, using a standalone custom tool.
- **Evidence:** Architecture and instruction reviews supported the dedicated-advisor responsibility but found core renderer, validator, proof, compaction, and model-route gaps. Execution-safety review identified that this repository's `global/` is an active `OPENCODE_CONFIG_DIR` and `global/plugin/` is auto-discovered, so source presence could activate the tool on a later restart without a separate installation operation.
- **Outcome:** Corrected to the retained strategy: dedicated advisor plus an explicitly configured, non-auto-discovered `global/extensions/specialist-catalog.ts` source, inert initialization, execute-local fail-closed behavior, and isolated profile proof.
- **Reason:** The corrected mechanism preserves one cohesive catalog owner and avoids unrequested active-host activation.
- **Do-Not-Repeat Condition:** Do not place the catalog source in an auto-discovered plugin directory, extend the mixed `session-env.ts` owner, expose a static roster, or treat source creation as installation authority.
- **Evidence-Based Retry Condition:** Use an auto-discovered source only if the active global source is no longer live or a separately authorized activation change proves exact containment and rollback; neither condition exists in this change.

## Strategy 5: Supersede Instruction-Size Ceilings With Context Quality

- **Objective:** Reconcile the retained advisor architecture with the repository's
  replacement instruction-context contract before implementation begins.
- **Approach:** Keep inventory size and token-proxy measurements as diagnostics while
  gating advisor/profile instruction changes on canonical ownership, exact-duplicate
  detection, mechanical canonicalization, context quality, and loaded behavior.
- **Evidence:** `replace-instruction-limits-with-context-quality` removed the maintained
  numeric instruction-budget owner. Advisor privacy, authority, profile, and behavior
  boundaries do not require a text-size maximum.
- **Outcome:** Selected as the current planning contract; the replacement change must
  apply first or this change must explicitly rebase before mutation.
- **Reason:** Unique advisor behavior must not fail solely because it increases a size
  proxy, while duplicate routing authority and behavior regressions must still fail
  closed.
- **Do-Not-Repeat Condition:** Do not restore `instruction:budget`, reviewed token-proxy
  ceilings, or compensating deletion requirements in this change.
- **Evidence-Based Retry Condition:** Reconsider a numeric instruction acceptance limit
  only if a separately accepted requirement identifies a concrete safety or runtime
  boundary that context-quality and loaded behavior checks cannot enforce.
