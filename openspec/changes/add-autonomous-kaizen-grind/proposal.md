## Why

Kaizen capture currently defaults to a fixed-slot store on the Windows system drive and leaves a large queue behind a manual 25-signal triage command that intentionally cannot implement improvements. A maintained workstation needs one explicit, reversible control that relocates the complete Kaizen lifecycle to the dedicated `D:\OpenCode\data\kaizen` root, continually drains every bounded backlog snapshot, and carries accepted project-owned improvements through visible project-local OpenSpec implementation without operator babysitting.

An admitted project or kit improvement launches a visible ordinary OpenCode root session from its registered owner project, creates the project-local OpenSpec change, immediately proposes/applies/proves/validates/archives it, and makes an explicitly authorized local commit; `/disable-kaizen-grind` symmetrically prevents new work and reaches terminal or isolated ownership for active automation without disabling capture.

- Introduce deterministic `/enable-kaizen-grind`, `/disable-kaizen-grind`, and `/kaizen-grind-status` front ends to one protected Kaizen Grind control plane with durable cycles/execution records/gates, global and per-member claims, exact daily/invocation budgets, one visible read-only triage session per cycle, automatic continuations through the same protected task, and cause-preserving diagnostics.
- Move the complete Kaizen store to a dedicated `D:\OpenCode\data\kaizen` root through a transactional SQLite v2 event/projection schema and a verified, restart-safe import/cutover/rollback path for the current JSON v1 store.
- Extend Work Campaign with a Kaizen remediation playbook selected through a distinct protected Grind registry and a standing onboarding-owned project-contained definition; convert evidence-confirmed owner-local execution records into frozen project missions while retaining Work Campaign as observer/orchestrator and Roadmap Mission as the sole source writer.
- Extend Roadmap Mission execution so each Kaizen change uses one ordinary visible root session in the target project's managed runtime, runs proposal then implementation in the same project/session, supports automation-to-user takeover, and completes proof, validation, archive, and explicitly authorized local commit before lifecycle resolution.
