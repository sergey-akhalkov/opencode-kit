# Strategy History

## 2026-08-26 - Keep One Long Grind Root And Rely On Compaction

- **Objective:** Complete multi-day discovered work without adding another durable workflow owner.
- **Approach:** Enable grind on one root, maintain a large todo list, use `session_delivery_context`, compaction summaries, project memory, and one large OpenSpec change until every audit and fix is complete.
- **Evidence:** The completion guard can keep one root moving and preserve bounded redacted evidence, but it does not own a roadmap or survive host/process loss as a source-of-truth workflow database. Project memory is advisory, compaction is bounded prose, and one OpenSpec change cannot safely freeze and checkpoint an unknown number of independently validated remediation outcomes.
- **Outcome:** Rejected.
- **Reason:** Transcript/context would remain the implicit cursor; coverage, writer liveness, dynamic backlog, and restart state could drift or exceed context limits.
- **Do Not Repeat Until:** The runtime provides a durable schema-correlated root workflow database with source-writer leases, project checkpoints, and exact restart reconstruction independent of transcript prose.
- **Evidence-Based Retry Condition:** Maintained installed evidence shows one root can survive process/host restart, retain complete large-scope coverage and dynamic work identities, and resume one source writer without new campaign artifacts or mission composition.

## 2026-08-26 - Put The Entire Audit And Every Fix In One OpenSpec Change

- **Objective:** Avoid campaign/portfolio complexity by using one proposal, design, spec set, and large task list.
- **Approach:** Finish the entire repository audit inside one change, append every finding as another task/spec, implement all fixes, and archive only when the whole repository is clean.
- **Evidence:** OpenSpec is a strong bounded-change owner, but discovered findings have different cohesive outcomes, write owners, proof boundaries, protected effects, and checkpoints. One all-or-nothing change cannot archive verified early outcomes or isolate failures while later findings continue to emerge.
- **Outcome:** Rejected.
- **Reason:** It creates an unbounded context/lifecycle unit, overlapping ownership, stale task/report state, and expensive global invalidation after every correction.
- **Do Not Repeat Until:** The accepted work is known before implementation and shares one cohesive outcome, owner, proof, checkpoint, and rollback boundary.
- **Evidence-Based Retry Condition:** A complete frozen audit demonstrates that all confirmed P0/P1 rows are one inseparable behavior change with one source owner and one validation boundary, rather than a portfolio.

## 2026-08-26 - Let The Roadmap Mission Dynamically Extend Its Queue

- **Objective:** Reuse the existing durable mission without adding a parent campaign controller.
- **Approach:** Allow the mission executor or completion arbiter to read audit/model output, append newly discovered slices, reorder dependencies, and continue after the original queue is exhausted.
- **Evidence:** `unattended-roadmap-orchestration` intentionally requires one immutable 1..100-slice definition, deterministic preflight, no model-derived successor, and one writer/checkpoint chain. Its replay and safety proof depend on those invariants.
- **Outcome:** Rejected.
- **Reason:** Dynamic queue mutation would make model prose lifecycle authority, invalidate mission replay/correlation, and merge discovery policy with source execution.
- **Do Not Repeat Until:** The mission capability is explicitly replaced with a different accepted contract and equivalent fail-closed dynamic-admission/replay evidence exists.
- **Evidence-Based Retry Condition:** A deterministic non-semantic admission mechanism can mutate a live mission queue while preserving exact intent, effects, writer ownership, checkpoints, restart replay, and all current manual mission compatibility; current evidence supports a parent freeze/handoff instead.

## 2026-08-26 - Use The Markdown Audit Report As Campaign State

- **Objective:** Keep campaign artifacts human-readable and avoid a structured ledger/materializer.
- **Approach:** Store file coverage, findings, resolutions, OpenSpec backlog, validation, residual risks, and current phase in one large Markdown document edited by each session.
- **Evidence:** `docs/feedbacks/audit-opencode-kit-2026-06-27.md` contains resolved findings alongside stale residual statements and manually maintained follow-up groups. The existing audit-ledger skill explicitly requires changed-block re-review but provides no executable projection/readback owner.
- **Outcome:** Rejected.
- **Reason:** One mutable narrative cannot reliably provide atomic transitions, stable identities, deterministic totals, stale-row detection, or restart cursor authority.
- **Do Not Repeat Until:** A validated Markdown schema can round-trip every seed fact and derived view without duplicate independently editable state.
- **Evidence-Based Retry Condition:** A maintained parser/materializer proves Markdown is the single normalized seed and rejects all stale/mixed variants with the same clarity and atomicity as structured records; otherwise Markdown remains a derived report.

## 2026-08-26 - Use A Recursive Agent Swarm As The Orchestrator

- **Objective:** Parallelize repository audit, planning, fixes, testing, and review with minimal controller code.
- **Approach:** Let audit agents dispatch more agents, allow writers to work in parallel, and trust summaries returned through the parent transcript to merge findings and decide completion.
- **Evidence:** Current agent contracts prohibit nested orchestration for leaf roles, require active-primary ownership, terminal writer closure, isolated/non-overlapping scopes, and main integration. A recursive swarm cannot durably prove child/process/write liveness after interruption or prevent two discovered fixes from overlapping.
- **Outcome:** Rejected.
- **Reason:** It replaces explicit state and leases with distributed transcript memory and creates unbounded coordination, self-review, and concurrent-writer risk.
- **Do Not Repeat Until:** The runtime exposes durable parent/child identity, isolated write authority, terminal liveness, persisted fan-in, and deterministic conflict handling for recursive execution.
- **Evidence-Based Retry Condition:** Installed evidence proves recursive workers reduce total time while preserving exact campaign state, no overlapping writes, complete coverage, and restart-safe fan-in better than bounded controller-owned read-only partitions.

## 2026-08-26 - Require Owner Approval Before Every Remediation Wave

- **Objective:** Prevent dynamic discovery from silently expanding scope or crossing protected effects.
- **Approach:** Pause after findings freeze and after every re-review so the owner approves work-item severity, grouping, OpenSpec changes, task order, and continuation.
- **Evidence:** The user explicitly selected autonomous wave creation/execution inside a fixed policy. Current authority permits main to update planning controls and dependency closure without owner approval when accepted semantics remain unchanged; protected product/effect choices remain separately owner-bound.
- **Outcome:** Rejected.
- **Reason:** Routine wave approval adds a manual multi-day bottleneck without improving safety for already preauthorized, finding-traceable P0/P1 work.
- **Do Not Repeat Until:** The accepted campaign policy changes or evidence shows deterministic admission plus protected-effect gates cannot prevent a specific unauthorized wave.
- **Evidence-Based Retry Condition:** A reproduced campaign admits a wave outside the accepted outcome/effects despite current freeze, traceability, reconciliation, ownership, and effect checks; then narrow only the failed decision boundary.

## 2026-08-26 - Support Every Host Platform And Playbook In The First Increment

- **Objective:** Make the mechanism universally reusable at initial delivery.
- **Approach:** Implement Windows Scheduled Task, systemd, launchd, multi-repository coordination, arbitrary discover/plan/execute/verify playbooks, and target-specific adapters in one change.
- **Evidence:** The current real host owner and recovery proof are Windows-specific; the user needs reuse across projects, not an unproved claim across every OS and workflow. Only audit-remediation has a concrete severity, coverage, and closure oracle in this discussion.
- **Outcome:** Rejected and narrowed.
- **Reason:** Cross-platform and arbitrary-playbook scope would delay the first complete real path, multiply protected lifecycle surfaces, and produce untested abstractions.
- **Do Not Repeat Until:** The Windows/reference campaign is working and another host or playbook is an accepted current requirement with a real boundary.
- **Evidence-Based Retry Condition:** A second maintained consumer demonstrates the same campaign core with one materially different host or playbook contract and identifies the minimal adapter seam from evidence.

## 2026-08-26 - Add A Separate Campaign Executor That Bypasses Roadmap Mission

- **Objective:** Simplify parent/child coordination by letting the new controller create OpenSpec changes, edit source, validate, archive, and checkpoint directly.
- **Approach:** Copy or reimplement mission process, session, writer, archive, checkpoint, retry, completion-guard, and proof behavior inside the campaign.
- **Evidence:** The mission already owns and has qualified those exact failure-prone boundaries. The architecture review identified duplicate orchestration/writer ownership as the primary risk and recommended frozen-wave input to the existing executor.
- **Outcome:** Rejected.
- **Reason:** It would create two mutation schedulers, two lease/state systems, duplicate archive/proof code, and ambiguous recovery after interruption.
- **Do Not Repeat Until:** The roadmap mission is removed or proven unable to execute a required frozen wave even after a narrow parent-correlation extension.
- **Evidence-Based Retry Condition:** A provider-free real OpenSpec fixture demonstrates an irreducible mission contract mismatch that cannot be solved with parent/work-item correlation and terminal handoff while preserving mission invariants.

## 2026-08-26 - Durable Campaign Above Frozen Missions With Windows Recovery

- **Objective:** Autonomously drive multi-day discovered work across bounded contexts and restarts while preserving scope, owner authority, and one source writer.
- **Approach:** Add one static-envelope/dynamic-portfolio campaign controller, normalized append-only state and ledger, isolated read-only semantic roots, fresh P0/P1 reconciliation and investigation, deterministic frozen-wave admission, existing mission execution, changed-block re-review, derived report, evidence-based convergence, and a separate portable supervisor with a thin protected Windows logon adapter.
- **Evidence:** Current guard, OpenSpec change, mission, audit-ledger, doctor, workstation, and proof owners each provide necessary lower-level contracts but no owner composes the complete lifecycle. User decisions authorize autonomous in-policy waves, Windows auto-resume, P0/P1-only remediation, and material-quality P1. The fresh architecture review confirmed the parent/mission separation, non-authoritative report, explicit unknown/effect gates, source-writer handoff, and active-change serialization as required risk controls.
- **Outcome:** Selected for proposal, delta specifications, design, and tasks.
- **Reason:** It is the smallest complete architecture that meets the accepted multi-day outcome without weakening the mission, foundation recovery, completion guard, protected boundaries, or unrelated work.
- **Do Not Repeat Until:** N/A - selected strategy.
- **Evidence-Based Retry Condition:** Provider-free contracts, real mission handoff, configured semantic proof, or installed Windows recovery disproves a specific selected boundary; revise only that boundary and preserve unaffected evidence rather than returning to a rejected broad mechanism.
