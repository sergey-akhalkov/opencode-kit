## Context

See `proposal.md` for motivation and PCR-001 scope. The current readiness reviewer receives original-request and candidate material in one brief. The bounded-falsification record tracks one reviewer session and challenge count but not candidate separation or continuation. The current focused pack supplies `representedRisk`, so it checks routing of a known issue rather than discovery from raw context. OpenSpec authoring already performs original-request failure foraging before drafting and the `task` adapter supports exact `task_id` continuation. Reordering reviewer reconstruction into that pre-authoring window is the smallest control that keeps the current candidate absent from prompt, files, and tool results without adding a session/workspace owner.

The active `make-team-advice-evidence-triggered` change owns several planned loaded-main, Change-Ready, fixture, capture, evaluator, and test roots. This change is planning-only and `mutationEnabled=false` until that change archives and exact ownership transfers. The mutation-disabled `add-autonomous-kaizen-grind` and `deliver-continuous-reusable-value` manifests place those changes after this one for shared or proof-dependent owners; pre-apply inventory must verify all three declarations and current roots rather than infer non-overlap.

## Goals / Non-Goals

**Goals:**

- Extend one existing semantic-readiness owner with a physically candidate-separated first phase and an identity-proven comparison continuation.
- Preserve one bounded episode, fresh corrected-candidate review, main disposition, exact Practice Owners, and honest evidence ceilings.
- Build one answer-free configured pack whose deterministic oracle can disprove separation, continuation, proportional routing, and expected finite-scenario behavior.
- Admit one short canonical principle only after the focused pack demonstrates value.

**Non-Goals:**

- A new reviewer, universal skill, semantic classifier, risk scorer, exhaustive future simulation, or retained evidence subsystem.
- Replacing substitution qualification, changing reviewer authority, or adding review to Ordinary Small exact work.
- Solving unobserved future variants or deriving project-domain rules from the motivating counterexample.

## Decisions

### 1. Extend the existing reviewer through one pre-authoring resumable protocol

After the original request and current raw evidence are sufficiently foraged but before `openspec new change`, proposal/design/spec/task creation, a session-local inline decision frame, or candidate source mutation, main launches `implementation-readiness-reviewer` once with no `task_id` for reconstruction. The first brief contains only original outcome/envelope facts and current raw source/system evidence. The candidate is not merely forbidden: neither a file candidate nor an inline-frame candidate exists in prompt or workspace, so normal reviewer search cannot return its bytes. After reconstruction returns, main creates the OpenSpec artifacts or smallest inline frame and resumes the exact returned task identity for comparison.

The phase-one response uses one role-local contract:

- privacy-safe reconstruction reference;
- actors and downstream consumers supported by evidence;
- state, lifecycle, ownership, recovery, and observability facts;
- distinctions whose downstream effects are supported or unknown;
- causal-use stop boundaries and evidence gaps.

The phase-two response retains the shared reviewer risk matrix and adds stable consequence fields: causal-use chain, discarded distinction, downstream observer/effect, reachable consequence, exact evidence or gap, earliest falsifier, and smallest mitigation. `no-material-finding` remains conforming. The reviewer never approves readiness. An already-existing candidate cannot retroactively receive this mode; it remains `single-stage` or `unknown`.

**Why not a new agent:** semantic readiness, task fit, and falsification already have one owner. A sibling would duplicate authority, trigger routing, and main disposition.

**Why not one prompt or a forbidden-path instruction:** the candidate bytes can still enter through ordinary project search; the first planning challenge reproduced that exact failure. Chronological nonexistence, not reviewer compliance, enforces the initial boundary.

**Why the configured capture now uses a directly routed reviewer child:** authoring order still makes the candidate absent without adding a workflow owner, but installed capture showed both that asking the root model to author `task` arguments can fail schema validation and that an SDK `subtask` may be followed by a parent model turn before capture regains control. That parent turn authored alternate candidate content and comparison before controller-owned materialization. The configured runner therefore reuses the maintained proof-server parent/child helper, sends the reconstruction directly to the configured reviewer child with mutation and nested-task tools disabled, reads back its exact route and evidence, then sends comparison to that same child. It submits each potentially long reviewer turn asynchronously and reads back a new assistant message only after that exact session becomes terminal, avoiding the SDK response-header timeout while preserving the same provider call and identity. This is a proof-runner transport correction, not another reviewer or production session owner. It proves installed reviewer behavior, temporal candidate-path absence, and continuation for the exercised session identity; it does not claim that every model-generated task argument will be valid or that direct proof transport exercises root-model task authoring.

### 2. Trigger on current distinction pressure, not general complexity

Main activates the two-phase variant only inside the existing decision-material readiness episode when a current decision can collapse evidenced differences in representation, identity, occurrence, actor, state, lifecycle, ownership, recovery, or proof outcome. This is a semantic judgment and remains outside deterministic automation. Material work without this pressure keeps the existing single-stage challenge; Ordinary Small exact work remains direct.

Skip/omit/cache/replay/emulation/replacement/bypass equivalence remains owned by `behavioral-substitution-qualification`. If both routes are relevant, its baseline/path/effect evidence can be part of the candidate-free raw context, but no second equivalence workflow or record is created.

**Alternative rejected:** applying two phases to every Material review would increase model/tool use without evidence that every decision benefits and would violate proportional routing.

### 3. Count a phase pair as one challenge and make continuity fail closed

Challenge count represents independent candidate challenges, not task calls. Pre-authoring reconstruction plus exact continuation for one candidate is challenge one. A confirmed decision-surface correction can start one fresh candidate-comparison child as challenge two using the frozen candidate-free reconstruction. It cannot resume the first candidate's reviewer or reconstruct context around the existing candidate. If the correction or new evidence invalidates the frozen reconstruction, challenge two remains unknown and the exact boundary moves to focused evidence or its Practice Owner. No third generic challenge is introduced.

The operation record gains optional protocol fields with a concrete compatibility need: currently active and archived records predate the protocol. Missing fields parse as single-stage evidence only. A new initial closed record requires `Protocol Mode: pre-authoring-separated`, a non-`none` reconstruction ref, `Candidate State At Reconstruction: absent`, and verified initial comparison continuity. Challenge count two additionally requires verified corrected-review freshness. Unsupported chronology, reconstruction currency, continuity, or freshness produces `unknown` plus unresolved evidence. Structural validation never claims that model reasoning was independent or correct.

### 4. Materialize the candidate only after answer-free reconstruction

The new focused pack keeps each scenario's raw context and candidate in controller-separated fields. Capture creates a disposable project that has no current candidate path or content, records that filesystem manifest, runs the loaded pre-authoring reconstruction including normal tool use, and records all stage-one prompt/file/tool-result facts. Only after reconstruction returns does capture materialize the candidate and resume the exact child. Expected distinction/consequence observations live in a separate reviewed evaluator contract and are never projected into model-visible files or prompts.

Preflight rejects actor-visible `representedRisk`, corrected artifacts, expected labels, premature file or inline-frame candidate materialization, path escape, unknown fields, unstable scenario order, and missing expected observations before any configured call. Evaluation performs exact comparison over capture-owned protocol/tool evidence and an explicit evaluator-only semantic-containment mode for every scenario: `required-consequence`, `required-unknown`, `evidence-bounded`, or `not-applicable`. It checks each file-candidate or inline-frame sentinel is absent from the pre-reconstruction filesystem/root prompt and every stage-one model-visible input/result, candidate creation follows reconstruction, the comparison uses the exact returned id, a corrected review uses a fresh reviewer and current frozen reconstruction, a completed candidate comparison reports at least one evidence-backed consequence where required or otherwise preserves honest `unknown`, routing controls stay proportional, no forbidden effects occur, and cleanup is terminal. The inline-frame and candidate-materialization chronology controls use `evidence-bounded`: either a closed result with at least one consequence and no unknown reason, or an unknown result with no consequence and an explicit reason is valid; every mixed or empty state fails. Their chronology and continuation oracles remain exact, while the insufficient-evidence control remains `required-unknown`. Natural-language consequence identifiers remain visible for manual evidence inspection but are not compared to hidden evaluator tokens because the live canary proved that derivation non-unique. It does not score prose, infer a good abstraction, or claim discovery superiority from one sample per arm.

The intentional second task call is pack-specific expected behavior, not a general friction regression. Provider and task bounds remain explicit. Provider-free tests cover parser/preflight/evaluator negatives; configured baseline/candidate capture is a separately authorized bounded run.

**Alternative rejected:** retaining `representedRisk` would only prove that the model can route a supplied answer and would not test the reproduced failure class.

### 5. Add the principle only after direct behavioral evidence

Implementation first creates the focused pack and candidate protocol wording, then runs the matched baseline/candidate comparison. The first matched live canary did not reproduce discovery superiority, so it does not authorize the proposed statement in `global/principles-of-work.md`; the canonical philosophy remains unchanged. The remaining full-population run proves only the narrowed protocol, containment, routing, safety, privacy, liveness, and cleanup claim.

After adding it, the final loaded candidate receives one matched rerun. If benefit is not reproduced, the principle is omitted and the candidate remains in development. This is retention evidence, not semantic authorization or universal proof.

### 6. Execute from independent proof leaves to loaded integration

The implementation dependency order is:

1. ownership transfer and current-source reread;
2. record/parser/validator compatibility and provider-free tests;
3. pre-authoring pack contracts, temporal candidate materialization, evaluator, and negative fixtures;
4. reviewer protocol and pre-authoring orchestration wording;
5. direct configured baseline/candidate observation;
6. conditional principle and final configured rerun;
7. loaded integration validation and strict OpenSpec checks.

Each leaf keeps its own earliest oracle. Deterministic record tests do not prove reviewer behavior; pack preflight does not prove loaded routing; configured scenario rows do not prove untested models or projects. The final integration oracle is the installed OpenCode entry point with exact source/model/environment identity and child/process cleanup.

## Failure Boundaries And Diagnostics

- Ownership overlap fails before production mutation with the exact change/root pair; planning artifacts remain readable.
- Fixture/preflight failure occurs before sessions or provider calls and preserves the contract path and cause.
- Stage-one failure preserves task status/stdout/stderr and starts no stage two.
- Premature file or inline-frame candidate creation prevents pre-authoring separation and produces single-stage or `unknown`; it is not repaired through a forbidden-path instruction.
- Missing or stale task identity prevents comparison and produces `unknown`; it is not retried through a candidate-visible substitute.
- A stale frozen reconstruction prevents generic corrected-candidate review and routes only the affected boundary to focused evidence or its exact owner.
- Stage-two or evaluator failure records the arm, scenario, sample, task identity, normalized field, exit status, stdout/stderr, effects, and cleanup without exposing private prompt content.
- Any open mutation-capable or proof-owned process/session blocks integration until terminal or isolated; proof cleanup targets only proof-owned identities.

## Proof Boundary

The current fidelity rung is provider-free parser, preflight, evaluator, validator, and fixture tests. The next real boundary is a bounded same-model baseline/candidate authoring sequence through the installed OpenCode entry point in disposable repositories: reconstruction first, candidate materialization second, exact continuation third. Existing local authorization permits the minimum synthetic configured calls required for this repository validation. Safeguards are generic non-sensitive prompts, explicit call bounds, no remote/product effects, isolated roots, exact process/session identity, and forbidden-effect sentinels. Cleanup removes only proof-owned temporary roots and terminates only proof-owned children after terminal evidence. PCR-001 bounds every result.

## Risks / Trade-offs

- **Model still misses a source-supported distinction** -> Keep claims finite, preserve raw evidence and exact expected observation, and leave unsupported scenarios failed or unknown rather than add vocabulary prompts.
- **Trigger becomes a generic complexity tax** -> Keep it inside the existing Material readiness episode and require current distinction pressure; retain direct Ordinary Small and single-stage Material controls.
- **Candidate already exists** -> Keep its evidence single-stage; do not retroactively claim separation or build isolation infrastructure solely to upgrade old evidence.
- **Continuation support differs by runtime** -> Require exact task identity; fail only the dependent readiness surface to `unknown` and preserve independent work.
- **Correction invalidates frozen context** -> Keep the corrected generic challenge unknown and use focused evidence or the exact owner rather than reconstructing around an existing candidate.
- **Legacy record compatibility masks absence of new evidence** -> Project missing fields only to `single-stage`, never to pre-authoring-separated success.
- **Evaluator leaks expected answers** -> Separate actor-visible seed projection from expected observations and test forbidden fields/tokens before configured calls.
- **Intentional extra task appears as friction regression** -> Use an explicit pack-specific task oracle and preserve general friction behavior unchanged.
- **Concurrent changes invalidate planned roots** -> Keep mutation disabled, rerun active ownership inventory, and reread every transferred source before apply.
- **Always-loaded wording adds cost without value** -> Add it only after the focused comparison improves and rerun the final loaded candidate once.
