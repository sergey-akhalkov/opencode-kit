## Why

Grind mode can still promote one blocked proof lane, process control, unavailable capability, or prematurely asked owner question into a pause of the entire root session. The loaded instructions already prefer path-scoped blocking, but the completion protocol has only global `continue` and `owner_required` outcomes, so the runtime cannot enforce that independent accepted work is drained before a user decision stops the root.

## Outcome Capsule

- **Outcome:** An explicitly grind-enabled root maintains a current task-scoped work frontier, parks only the dependency cone affected by a gate or unresolved decision, and continues every dependency-valid accepted-scope item before asking the owner. A blocking user question is emitted only for a material product decision when no independent runnable item remains; process controls, access/capability conditions, technical failures, safety gates, and proof-path gates never become global product questions or false completion.
- **Operating Envelope:** Parentless roots using the installed completion guard, its root-correlated `grind_frontier` tool, hidden completion arbiter, OpenSpec apply workflow, and grind-backed roadmap/campaign execution; one bounded versioned frontier containing current accepted work items, dependency edges, gate refs, parked product decisions, and controller-derived runnable refs; existing local standing authority and configured tool permissions; current supported OpenCode question reply/reject and synthetic continuation APIs. The controller validates shape, correlation, and graph readiness but never infers product semantics.
- **Non-Goals:** Bypassing credentials, permissions, licensing, safety interlocks, writer-liveness, restoration, cleanup, live-attempt, destructive, remote, deployment, release, cost, or legal boundaries; continuing impossible work while the host or required model is unavailable; unbounded unchanged retries or provider calls; deterministic classification of arbitrary prose as a product decision; a general workflow database; replacing OpenSpec tasks, autonomous campaigns, or human interruption; speculative work that depends on an unresolved product choice.
- **Non-Deferrable Invariants:** `/disable-grind`, explicit user interruption, and session deletion retain immediate authority. A gate blocks only work items that reference it or depend on them. The runtime computes readiness from the reviewed frontier and rejects a global product-decision pause while any current item is runnable. Only a material decision that changes accepted product behavior or another protected product semantic and lacks an accepted reversible default may become `product_decision_required`. Technical, process, access, safety, and external constraints remain enforced but are represented as scoped gates or honest resumable waiting states. Synthetic question deferral never becomes a human answer. No waiting state is completion, and no alternate lane clears the blocked lane's evidence or Live-Attempt Gate.
- **Observable Proof:** Through the installed grind entry point in disposable roots, reproduce the circular stop-line/live-attempt case and observe autonomous process-control reconciliation plus continuation without a question; park a product decision that blocks task A while task B completes before the question is surfaced; preserve a true all-remaining-work product decision as the only blocking question; park missing credential, capability, technical, safety, and proof-path gates while independent work runs; reject and clear prematurely invoked product and non-product blocker questions through the official question rejection path, then resume runnable work or enter honest non-product waiting; prove completion only after all accepted work closes; and prove that user interruption, protected effects, stale frontiers, cycles, unknown writer liveness, and unchanged failed strategies remain fail-closed.
- **Material Residual Risks:** The main model can misclassify a dependency or product decision before writing the frontier; stale or incomplete work inventories can hide runnable work; rejecting a pending question changes the current tool-call path and can race a human reply; automatic continuation can increase model cost or loop if progress identity is weak; ordinary roots without durable OpenSpec tasks need a compact frontier owner; campaign and root semantics can drift if only one layer is updated. Deterministic graph validation, fresh arbitration, progress fingerprints, bounded execution epochs, race-safe provenance, paired safety controls, and installed behavior proofs reduce but cannot eliminate model-sensitive classification risk.
- **Stop Line:** Finish one versioned task-scoped frontier contract, deterministic readiness and correlation checks, parked-decision and scoped-gate projection, premature-question deferral, completion-guard verdict/state changes, bounded execution-epoch rollover without process-to-owner escalation, aligned main/OpenSpec/roadmap/campaign routing, focused validation, and installed matched behavior proof. Stop before a generic distributed scheduler, arbitrary permission auto-granting, remote credential acquisition, automatic protected effects, semantic scoring helpers, product-roadmap generation, or unattended work outside the accepted root scope.
- **Delivery Horizon:** none - this is a bounded correction to the existing grind lifecycle and is not linked to a declared project Delivery Horizon.
- **Automation Dividend**: required - extend the maintained session-completion-guard and pre-escalation proof owners with one versioned frontier fixture/materializer and matched installed scenarios for partial product, process, access, safety, proof-path, completion, and interruption outcomes; provider-free replay must validate graph readiness, verdict legality, question races, stable ordering, and side-effect bounds without scoring product semantics.
- **Bounded Falsification Review**: required - task-frontier ownership, product-decision threshold, deterministic versus model-owned classification, question-deferral safety, process-budget rollover, ordinary-root persistence, roadmap/campaign alignment, failure visibility, and protection against infinite or unsafe continuation.

## Claim And Evidence Scope

- **Claim ID:** `GRIND-TSB-001`
- **Claim Class:** finite-population loaded workflow and runtime behavior.
- **Population:** Reviewed scenarios for circular process stop-line, partial product decision, all-remaining-work product decision, missing credential/capability, technical blocker, safety/protected gate, blocked proof lane with independent route, premature pending question, stale/cyclic/malformed frontier, unchanged failed strategy, execution-epoch exhaustion, explicit interruption, and completed outcome.
- **Coverage Basis:** Deterministic frontier fixtures and parser/controller tests; matched same-model baseline/candidate roots with identical accepted work, permissions, environment, and initial state; installed question and continuation event capture; provider-free replay of preserved bundles; roadmap/campaign composition controls; and current project-native validation.
- **Production Path:** Loaded main records or reconciles the current frontier -> controller validates and derives runnable items -> hidden arbiter maps current requirements and gates -> guard continues the next runnable item, defers and parks a premature question, enters a non-terminal waiting state, presents one terminal product decision, or allows stop after complete closure.
- **Comparison Paths:** Current global-verdict behavior; disabled grind; autonomous in-authority question answering; true product-decision-only stop; blocked lane with and without an independent sibling; explicit user interruption; and malformed/stale frontier controls.
- **Environment:** Current supported local OpenCode, configured kit global source, exact primary and arbiter model routes for loaded captures, disposable Git/OpenSpec projects, isolated proof state, existing standing local authorization, and no target-project remote, deployment, release, credential mutation, or destructive effect.
- **Real Oracle:** Root/child/question events, official reply/reject effects, frontier and guard metadata, derived runnable refs, tool calls, changed paths, task and requirement closure, verdict/state transitions, exact diagnostics, provider-call counts, terminal process/session ownership, and cleanup readback.
- **Unresolved Observations:** Product-decision and dependency quality outside the maintained scenarios; long-running behavior beyond the reviewed frontier and evidence bounds; provider/host outages with no executable work; project-local permission policies that deny required operations; other OpenCode versions; and whether a later general mission runtime should consume the same frontier schema.
- **Maximum Claim:** In the reviewed installed environment and finite scenario population, grind prevents a scoped gate or parked decision from becoming a global owner question while independent accepted work remains, without bypassing the gate or claiming completion. It does not guarantee progress when no executable route exists, universally correct product classification, unlimited cost, compatibility with untested runtimes, or authorization for protected effects.

## What Changes

- Add one plugin-owned `grind_frontier` tool that derives root identity and basis refs from the current tool context, validates and atomically persists a complete candidate frontier, and returns its server generation plus controller-derived runnable refs; invalid input never replaces the last valid frontier.
- Add the versioned task-scoped frontier to completion evidence with stable work-item, dependency, gate, parked-decision, progress, and runnable references; keep semantic classification model-owned and graph readiness deterministic.
- Replace global `owner_required` semantics with a product-decision-only terminal path plus scoped non-terminal waiting states for external, technical, safety, and capability conditions.
- Require main and OpenSpec apply to drain every dependency-valid accepted item before presenting a parked product decision, and change independent work from optional to mandatory continuation.
- Defer any prematurely asked blocker question that is not currently eligible for a human product decision by race-safely rejecting the pending request, recording product-decision or non-product-gate provenance, and either injecting one bounded continuation for the selected runnable item or entering non-product waiting when the frontier is empty.
- Keep autonomous offered-label questions on the existing official reply path; never infer a free-form answer or convert deferred/rejected input into human authority.
- Separate finite execution/audit attempt budgets from mission completion: exhaustion checkpoints the current frontier and rolls to an eligible bounded successor or enters an honest non-product waiting/error state, never an owner decision.
- Align grind-backed roadmap missions and autonomous campaigns so one blocked slice/item cannot prevent an unrelated authorized dependency-valid sibling from running; only an empty runnable frontier can produce terminal product-decision handoff.
- Add exact diagnostics and matched baseline/candidate proof for frontier provenance, stale/cyclic input, question races, scoped Live-Attempt Gates, protected-effect controls, no-progress suppression, and terminal cleanup.

## Capabilities

### New Capabilities

None.

### Modified Capabilities

- `session-completion-guard`: Add task-scoped frontier evidence and enforcement, product-decision-only terminal questions, premature-question deferral, non-product waiting states, and process-budget behavior that cannot manufacture owner scope.
- `library-change-ready-sdlc`: Make independent accepted work mandatory when one dependency chain is blocked and distinguish scoped action gates from global product decisions.
- `library-instruction-artifacts`: Align loaded main and arbiter instructions, question routing, completion semantics, and installed behavior evaluation around the task-scoped frontier.
- `library-spec-workflow-integrity`: Require apply to reconcile dependencies, park decision cones, and continue the next runnable accepted task before a blocking product question.
- `unattended-roadmap-orchestration`: Continue dependency-valid authorized slices around scoped product, access, process, capability, and live-attempt gates instead of globally stopping at the first blocked slice.
- `autonomous-work-campaign`: Make separate authorized sibling waves mandatory before terminal product-decision handoff and preserve non-product waits without false completion.

## Impact

- Runtime owners: the completion-guard plugin tool registration plus `global/extensions/session-completion-guard/{controller,types,verdict,question,runtime-support,status}.ts`, session-delivery/arbiter evidence projection, and the hidden `session-completion-arbiter` contract.
- Loaded workflow owners: `global/AGENTS.md`, Change-Ready and OpenSpec apply surfaces, project templates/mirrors, and grind-backed roadmap/campaign execution contracts.
- Proof owners: existing completion-guard, autonomous-question, pre-escalation recovery, roadmap mission, campaign, contract, and installed runtime proof families; no second general proof runner is introduced.
- Persisted root metadata gains a versioned bounded frontier and parked-decision provenance. Compatibility and restart behavior must be explicit; malformed, unsupported, stale, or cyclic state remains visible and fail-closed.
- Reuse disposition: `extend` the completion guard as the lifecycle owner and reuse campaign work-item/dependency concepts without importing its full scheduler into ordinary roots. New code is limited to the smallest frontier validation/projection seam required to prevent the controller from trusting a global prose verdict.
- Profile: `Material` because implementation changes loaded lifecycle, question handling, persisted root metadata, concurrency/race behavior, and safety-sensitive continuation. Planning artifacts remain `Development-Stage: development` and authorize no install, activation, provider-cost expansion, credential use, protected effect, commit, push, release, deployment, or remote mutation.
