# Strategy History

## 2026-08-31 - Separate successor instead of expanding delivery checkpoints

- **Objective**: Select the smallest owner for proactive recursive task decomposition.
- **Approach**: Compare extending `add-outcome-preserving-delivery-checkpoints` with creating a successor capability.
- **Evidence**: The active predecessor reacts to established delivery drag and is already in final qualification tasks, while the requested behavior triggers before the first parent integration action and has distinct proportional controls and proof scenarios.
- **Outcome**: Selected a separate successor change with an archive-before-acquire dependency on overlapping owners.
- **Reason**: Expanding the predecessor would mix proactive task-shape semantics with reactive route-reconsideration semantics and invalidate its nearly complete evidence population.
- **Do Not Repeat**: Do not fold leaf-first decomposition into the predecessor while its accepted outcome and candidate remain unchanged.
- **Retry Condition**: Reconsider a combined owner only if current canonical evidence after predecessor archive proves the two triggers cannot be expressed or validated independently.

## 2026-08-31 - Reuse the flat dependency DAG

- **Objective**: Represent leaf-before-parent ordering with the least new runtime mechanism.
- **Approach**: Compare a new hierarchical task-network/frontier schema with existing OpenSpec tasks and grind `dependsOn` edges.
- **Evidence**: Frontier schema v1 already stores stable items, explicit dependencies, gates, requirement refs, evidence refs, validates acyclicity, and derives runnable items without semantic inference.
- **Outcome**: Selected existing tasks plus the flat dependency DAG; no parent field, OR-edge, planner store, or schema migration.
- **Reason**: The missing behavior is semantic decomposition and honest task reconciliation, not structural readiness computation.
- **Do Not Repeat**: Do not add a hierarchy schema merely for navigation or because the conceptual model is drawn as a tree.
- **Retry Condition**: Reconsider schema expansion only if an accepted current scenario cannot preserve required ordering, gating, or evidence attribution with existing item ids and dependencies.

## 2026-08-31 - Use evidence boundaries instead of numeric granularity

- **Objective**: Define a project-neutral minimum leaf without over-decomposing routine work.
- **Approach**: Compare numeric file/task/unknown/duration thresholds with an evidence-based independent-failure and proof-boundary criterion.
- **Evidence**: File counts and elapsed time do not reliably distinguish cohesive work from independently failing prerequisites across UI, network, build, hardware, and proof tasks; current kit principles also reject proxy optimization.
- **Outcome**: Selected a semantic leaf contract with explicit direct, mechanical-grouping, same-leaf, and inseparable-integration controls.
- **Reason**: Independent owners, boundaries, oracles, and cleanup paths identify actionable isolation while avoiding Goodhart pressure.
- **Do Not Repeat**: Do not introduce a universal numeric granularity score or depth limit for unchanged evidence.
- **Retry Condition**: Reconsider bounded numeric fields only for explicit storage or runtime capacity safety, never as semantic task-quality inference.
