## Why

The kit tells main to choose the smallest dependency-valid slice and can react when expensive downstream attempts stagnate, but it does not define when a compound task must be recursively split before execution. As a result, independently failing prerequisites can remain hidden inside one checklist item and main can repeatedly exercise a broad parent scenario while trying to diagnose several unrelated causes at once.

## Outcome Capsule

- **Outcome**: Every installed kit primary session decomposes non-trivial compound work into the smallest useful evidence-bearing leaves before a dependent costly or integration action, executes and proves those leaves before their parent, and recursively introduces a new child task when current evidence exposes an independent unresolved prerequisite. Ordinary Small cohesive work remains direct, and OpenSpec/grind roots preserve the same decomposition through their existing task and frontier owners.
- **Operating Envelope**: Loaded global main instructions and maintained OpenSpec propose/apply behavior on the supported OpenCode runtime; Ordinary Small and Material work; ordinary, OpenSpec, and explicitly grind-enabled parentless roots; current user requirements, source/runtime evidence, accepted task artifacts, and controller-derived frontier state; model-owned semantic decomposition projected into existing tasks and dependency edges; no new planner service, scheduler, persistence layer, or deterministic semantic inference.
- **Non-Goals**: Decomposing every file edit, imposing numeric task-size limits, replacing outcome capsules or proof ladders, constructing a permanent project-management tree, optimizing global critical paths, adding a planning agent, requiring grind, weakening dependency-valid independent work, or turning optional cleanup and polish into accepted scope.
- **Non-Deferrable Invariants**: Decomposition preserves the accepted outcome, operating envelope, proof population, authorization, safety, restoration, cleanup, and claim ceiling. A child is introduced only for required dependency closure, not because an implementation detail is interesting. Parent integration does not run while a required child is unresolved; child success does not prove its parent or a sibling; independent accepted work remains runnable; a product or protected-action boundary retains its existing gate; and planning changes never authorize the underlying action.
- **Observable Proof**: Through the installed configured kit in unrelated disposable projects, exercise at least: a compound ordinary task with two independent prerequisites; a coarse OpenSpec task before its first integration action; a new independent failure discovered during a leaf; an integration-only failure after all prerequisites pass; a grind parent with multiple child dependencies and an independent sibling; a cohesive Ordinary Small task; and grouped mechanical edits under one owner/oracle. Observe root-to-leaf planning, leaf-to-root proof, parent suppression until required children close, recursive task/frontier correction without a user process question, preserved independent work, no false parent completion, and no decomposition ceremony for controls.
- **Material Residual Risks**: Model-owned leaf classification can over-split cohesive work or leave a compound task too coarse; instruction-only ordinary sessions lack deterministic semantic enforcement; recursive task correction can create planning churn; a wrongly classified child can hide a changed product decision; existing task text may not expose real dependencies; and this change overlaps active loaded-main, OpenSpec apply, completion-frontier, and shared proof owners.
- **Stop Line**: Finish one project-neutral leaf contract, proactive and failure-triggered recursive decomposition, parent/child execution rules, ordinary/OpenSpec/grind continuity, proportional negative controls, focused deterministic drift checks, and installed behavior proof. Stop before a new task-tree schema, planner or optimizer agent, numeric complexity score, universal duration threshold, project-management UI, background scheduler, automatic cross-project mutation, or consumer-project implementation.
- **Delivery Horizon:** none - this is a universal kit workflow correction and is not part of a declared product delivery horizon.
