# Strategy History

## 2026-09-01 - Reject output volume and mandatory recall as continuous value

- **Objective:** Make reusable delivery continuous without optimizing for helper, document, checkpoint, or search-report counts.
- **Approach:** Compare declaring every finished artifact as value and requiring a reusable-capability recall checklist with a consumer-grounded readiness boundary integrated into current foraging and proof.
- **Evidence:** The canonical philosophy already makes working behavior and real consumer boundaries primary; current reuse instructions already route mechanism uncertainty and exempt trivial owner-local work. A helper or direct component check can pass without a production consumer or parent integration.
- **Outcome:** Selected real consumer, direct proof when truthful, parent integration, reachability, discoverability, and retirement as the foundation readiness contract; retained direct handling for cohesive and trivial work.
- **Reason:** This makes value falsifiable without turning artifact production or search ceremony into a proxy target.
- **Do-Not-Repeat Condition:** Do not add helper quotas, universal pre-edit recall, mandatory receipts, or checkpoints for work with no distinct reusable boundary.
- **Evidence-Based Retry Condition:** Reconsider only if current installed scenarios show a required reusable capability cannot become visible or discoverable through the selected owner and ordinary progress/handoff surfaces.

## 2026-09-01 - Reject a central capability registry and demand ledger

- **Objective:** Make reusable value discoverable and retireable without stale central synchronization.
- **Approach:** Compare a capability/demand registry with federated discovery through current source, references, package/config roots, OpenSpec capabilities, documentation links, and configured code intelligence.
- **Evidence:** The archived private reuse-registry change was abandoned; current `reuse-discovery` already owns bounded search order and honest degraded evidence, while source/config/runtime facts remain authoritative for consumption.
- **Outcome:** Selected federated discovery with no registry, promotion lifecycle, demand ledger, or default-on memory.
- **Reason:** The missing contract is consumer readiness and reachability, not another semantic database.
- **Do-Not-Repeat Condition:** Do not revive registry synchronization or treat memory/catalog presence as stronger than current source and runtime roots.
- **Evidence-Based Retry Condition:** Reconsider a retained index only if repeated current source-backed failures prove a specific bounded discovery fact cannot be obtained at lower total lifecycle cost and the index has one truthful freshness/retirement owner.

## 2026-09-01 - Use the first production consumer as readiness and later consumers as reuse evidence

- **Objective:** Avoid both speculative foundations and an arbitrary two-consumer threshold before useful reuse.
- **Approach:** Compare helper creation, first production consumption, and second production consumption as the value boundary.
- **Evidence:** One production consumer supplies real demand and parent integration; requiring two consumers delays an already useful proven capability, while creation alone supplies no demand. A second distinct consumer provides direct evidence that the capability was reused.
- **Outcome:** Selected first-consumer `Value Ready` and second-consumer observed reuse.
- **Reason:** This is the earliest real demand boundary and preserves Rule of Three against speculative abstractions.
- **Do-Not-Repeat Condition:** Do not require a hypothetical or second consumer before first readiness and do not count tests, fixtures, or documentation mentions as consumers.
- **Evidence-Based Retry Condition:** Reconsider only if current production evidence shows first-consumer readiness systematically creates capability boundaries without a truthful independent contract, oracle, or retirement path.

## 2026-09-01 - Reuse Knip instead of building or expanding an inventory graph

- **Objective:** Reject supported TypeScript module/export dead code without owning a new parser or mixing inventory responsibilities.
- **Approach:** Compare custom regex scanning, a custom TypeScript AST/import graph, extending `project-inventory.ts`, and a pinned mature production-mode analyzer behind one owner-local validator.
- **Evidence:** `project-inventory.ts` owns root classification rather than symbol resolution. Knip source and metadata expose unused file/export analysis, explicit entry/project patterns, production mode, JSON output, and Node 24 support. Runtime repository fit is still unproven.
- **Outcome:** Selected pinned Knip for the supported graph, extended existing validation orchestration, and limited new code to exact root/baseline/process normalization glue.
- **Reason:** Reuse minimizes parser/resolution ownership while keeping the kit's semantic roots and failure policy explicit.
- **Do-Not-Repeat Condition:** Do not add regex/AST graph logic or turn project inventory into reachability analysis while Knip satisfies the characterized contract.
- **Evidence-Based Retry Condition:** Reconsider the analyzer only if task 1.3 or later current runtime evidence proves a required supported root/finding cannot be represented safely and no configuration or narrow adapter correction preserves the accepted claim.

## 2026-09-01 - Exclude tests from liveness and preserve dynamic unknowns

- **Objective:** Prevent test-only code from surviving while avoiding unsafe deletion of externally or dynamically activated behavior.
- **Approach:** Compare test-inclusive graph roots, production-only roots, broad public/plugin ignores, and explicit reviewed roots with unresolved edges reported separately.
- **Evidence:** Tests prove behavior but are not production demand. Package scripts, CLI/plugin/extension/public/generated-profile and reviewed dynamic entrypoints can be real consumers, while unsupported reflection cannot be disproved by static silence.
- **Outcome:** Selected production-mode exclusion of tests, exact root/source references, and `unknown` for unsupported dynamic/external edges.
- **Reason:** This rejects exercised dead code without converting analyzer limits into false absence claims.
- **Do-Not-Repeat Condition:** Do not use tests, proof fixtures, examples, documentation, blanket ignores, or speculative roots as production liveness evidence.
- **Evidence-Based Retry Condition:** Revise root support only when a current runtime source or fixture proves an additional activation class and supplies an exact source reference and safe oracle.

## 2026-09-01 - Prefer exact self-cleaning baseline rows over budgets or legacy cleanup

- **Objective:** Introduce a useful gate without hiding new findings or expanding into unrelated whole-repository cleanup.
- **Approach:** Compare fail-on-any-current finding, numeric budgets, wildcard ignores, exact accepted findings, and immediate legacy cleanup.
- **Evidence:** Before installation the current finding set is unknown. Numeric budgets allow replacement, wildcard ignores hide last-consumer removal, and broad cleanup is outside the accepted increment. Exact rows can fail both new and stale debt.
- **Outcome:** Selected no baseline when clean and an optional generated exact baseline with reviewed reasons, version/config identity, exact set difference, and stale-row failure when current debt must remain.
- **Reason:** The selected control rejects new debt and forces baseline shrinkage without representing accepted debt as live code.
- **Do-Not-Repeat Condition:** Do not add count budgets, prefixes, blank reasons, wildcard suppressions, or baseline rows for current-change findings.
- **Evidence-Based Retry Condition:** Reconsider only after current characterization proves exact row identity cannot remain stable under a pinned analyzer and reviewed configuration.

## 2026-09-01 - Keep value visibility as an ordinary progress fact

- **Objective:** Expose completed reusable value inside a larger unfinished outcome without creating another checkpoint or lifecycle owner.
- **Approach:** Compare a named `Value Checkpoint` protocol with one bounded ordinary progress/handoff fact.
- **Evidence:** Architecture review found that `Value Checkpoint` collided with the existing `Delivery Checkpoint State` continuation/process contract and that draft deltas used inconsistent `SHALL`/`MAY` obligations.
- **Outcome:** Renamed the behavior to a mandatory value progress fact only for a completed reusable unit inside unfinished parent work and explicitly forbade checkpoint identity, process gate, suppression, continuation, retained artifact, and completion effects.
- **Reason:** Ordinary visibility satisfies the value outcome while preserving one existing delivery-checkpoint owner.
- **Do-Not-Repeat Condition:** Do not add a value checkpoint schema, identity, process state, compaction block, or completion meaning.
- **Evidence-Based Retry Condition:** Reconsider the visibility surface only if installed scenarios prove ordinary progress/handoff cannot preserve the unit, consumer, proof boundary, and unresolved parent dependency distinctly.

## 2026-09-01 - Separate read-only validation from explicit baseline materialization

- **Objective:** Prevent strict validation, pre-push, and CI from hanging, leaking temporary state, or writing accepted-debt configuration.
- **Approach:** Compare one mixed check/write validator mode with a read-only validation API and a thin explicit materialization CLI over the same semantic owner.
- **Evidence:** Architecture review found the draft assigned analyzer child process, temporary configuration, and baseline writes to one owner without production-path timeout, terminal closure, `finally` cleanup, or a hot-path read-only guarantee. Existing repository validation is read-only and other child-process owners use bounded timeouts.
- **Outcome:** Selected a read-only check API with timeout/terminal cleanup and an explicit named-target materialization mode unreachable from strict validation, pre-push, CI, or default checks.
- **Reason:** The split preserves one semantic owner while separating incompatible effect boundaries and failure contracts.
- **Do-Not-Repeat Condition:** Do not make validation write roots/baselines, invoke analyzer through shell interpolation, return before child closure, or leave temporary cleanup to fixtures alone.
- **Evidence-Based Retry Condition:** Reconsider the adapter shape only if current implementation evidence proves the same explicit effect separation cannot be maintained through one owner and thin CLI.
