## Why

The kit already prefers small proven capabilities, direct capability proof, parent integration, reuse, and evidence-backed workflow automation, but it has no complete lifecycle for recognizing a finished reusable unit as delivered value, making that value visible without another completion stage, or preventing a capability from becoming dead code after its last production consumer disappears. Without a bounded operational contract, "continuous value" can collapse into speculative helper creation, mandatory search reports, or stale registries instead of making later work simpler.

### Outcome Capsule

- **Outcome**: Loaded main continually delivers the smallest finished product, foundation, or knowledge value that advances the accepted outcome. Foundation value becomes ready only with one semantic owner, a bounded contract, direct proof when truthful, one real production consumer, distinct parent integration proof, federated discoverability, supported production reachability, and an explicit retirement path. A second observed consumer confirms reuse without creating a registry or mandatory report. In this kit, one deterministic TypeScript gate rejects new module/export-level dead code and newly orphaned supported capabilities while keeping tests from satisfying production reachability; portable instructions require a project-native analyzer when available and report automatic assurance `unknown` when the project cannot support it.
- **Operating Envelope**: The current private Node 24 TypeScript/JavaScript kit; loaded working philosophy and main workflow instructions; existing semantic-owner, reuse, leaf-first, direct-capability, parent-integration, validation, documentation, and handoff owners; pinned development-only TypeScript analysis; explicit package-script, CLI, plugin, extension, generated-profile, and other reviewed runtime roots; provider-free disposable TypeScript fixtures; bounded same-model installed OpenCode scenarios in disposable projects; and no installation, activation, remote effect, or consumer-project mutation.
- **Non-Goals**: A central capability registry, demand ledger, value score, helper quota, per-leaf search receipt, universal pre-edit search, universal multi-language analyzer, whole-repository legacy dead-code cleanup, speculative public APIs, one task/function/file per value unit, automatic semantic Markdown judgment, default-on project memory, publication of helpers across projects, or changing public product/API, persisted-data, security, privacy, release, or deployment semantics.
- **Non-Deferrable Invariants**: Outcome remains more important than the number or frequency of value progress facts. A helper, document, test, task, file, module, or green component check alone never proves delivered value. Tests and proof fixtures cannot keep production code alive. Source, package/config/runtime entrypoints, current proof, and explicit external/dynamic-root evidence outrank documentation and memory. Unsupported dynamic resolution remains `unknown` and cannot authorize deletion. A last-consumer removal must retire the supported internal capability or preserve it through a truthful current root; blanket ignores and speculative future consumers cannot satisfy the gate. Direct capability evidence never substitutes for parent integration. A value progress fact is ordinary visibility and never a `Delivery Checkpoint State`, process gate, completion signal, or retained lifecycle record. Deterministic tooling validates explicit graph, root, finding, baseline, fingerprint, path, and schema facts only and never infers semantic value, owner fit, documentation truth, or portability.
- **Observable Proof**: Through a pinned production-mode TypeScript analysis entrypoint and disposable fixtures, accept one capability reachable from a production root, a second production consumer, and each reviewed CLI/plugin/public/dynamic root; reject an unused new file/export, a capability referenced only by tests, a transitively unreachable internal chain, and a capability orphaned by last-consumer removal; fail closed on malformed roots, analyzer failure, stale baseline identity, and unsupported suppression. Through the actual installed OpenCode entrypoint, matched scenarios deliver one owner-local capability with direct and parent proof plus one non-completing value progress fact, reuse a discoverable existing capability for a second consumer, remove an orphan after its last consumer, keep a cohesive direct implementation unfragmented, perform no extra value ceremony for a trivial fix, and report portable automatic assurance `unknown` where no project-native analyzer exists. Documentation scenarios accept current executable/source-linked knowledge, invalidate a changed fingerprint or failed example, and make no semantic-freshness claim from structure alone.
- **Material Residual Risks**: The initial root inventory or analyzer configuration may contain false roots, unresolved dynamic loaders, or pre-existing findings; a reviewed baseline can preserve existing debt and itself become stale; TypeScript/Knip version changes can alter findings; static analysis cannot prove every reflective or external consumer; loaded behavior remains model-sensitive; documentation can remain semantically wrong despite green structural links; value progress facts can become noisy; finite fixtures do not prove every language, repository, model, or runtime; and concurrent dirty changes overlap instruction, validation, proof, and OpenSpec owners.
- **Stop Line**: Finish the canonical continuous-value principle, compact loaded application, product/foundation/knowledge readiness and retirement semantics, non-completing value progress visibility, federated discovery and observed-reuse behavior, pinned kit TypeScript reachability/root/baseline gate, last-consumer cleanup, bounded documentation freshness, portable analyzer-or-unknown policy, provider-free fixtures, installed behavior evidence, and current validation/readback. Stop before universal analyzers, a capability registry, demand telemetry, value metrics, broad legacy cleanup, public helper publication, semantic documentation scoring, default-on memory, installation/restart, release, deployment, or remote effects.
- **Delivery Horizon:** none - this is a standalone universal kit workflow and validation increment, not part of a declared project Delivery Horizon.

- **Population**: Product value at a real consumer boundary; one owner-local foundation capability with a first production consumer, direct oracle, and parent integration; a second consumer reusing the same capability; a cohesive direct implementation with no truthful lower capability boundary; a trivial fix; an unused new file/export; test-only use; an unreachable internal chain; last-consumer removal; package-script/CLI/plugin/public/dynamic roots; malformed, stale, unresolved, and unsupported root/baseline cases; current executable/source-linked documentation; changed source fingerprints; failing executable examples; and an unrelated project with and without an applicable project-native analyzer.
- **Coverage Basis**: Reviewed root/config/baseline seed data, pinned analyzer output, provider-free disposable TypeScript projects, deterministic positive and red controls, focused validator and orchestration tests, and matched same-model installed OpenCode scenarios with identical prompts, permissions, source/model/profile/environment identities, file/effect oracles, and cleanup boundaries.
- **Production Path**: Loaded `global/principles-of-work.md` and `global/AGENTS.md`, Universal Development Loop and maintained project mirror, current reuse and capability-composition instructions, project/package/runtime root manifests, the repository validation orchestrator and CI/pre-push consumers, a pinned development-only TypeScript analyzer, existing consumer-outcome and capability-composition proof families, and project-native validation in unrelated disposable projects.
- **Comparison Paths**: Current outcome/direct-proof workflow without value readiness or retirement, a prose-only mandatory recall/checklist candidate, a central registry/demand-ledger candidate, custom regex/AST graph candidates, existing project/code-quality inventories, test-inclusive analysis, blanket ignore/budget baselines, and projects with unsupported analyzers.

It does not prove universal dead-code absence, semantic documentation correctness, cross-project portability, or improvement in every model, language, or repository.

## Automation Dividend

- **Automation Dividend**: required - add one maintained production-reachability validation owner that invokes the pinned analyzer, normalizes root/config/finding/baseline facts in stable order, and serves focused fixtures, strict validation, pre-push, and CI without duplicating analyzer argv, parsing, or exception policy.
- **Bounded Falsification Review**: required - challenge output-as-value substitution, speculative helper pressure, missing first-consumer or parent proof, test-only liveness, false or blanket roots, stale baseline acceptance, last-consumer escape, dynamic/public overclaim, unsupported portable enforcement, documentation-freshness overclaim, noisy progress-fact behavior, and unnecessary registry/framework scope.

## What Changes

- Define product, foundation, and knowledge value plus the exact readiness, observed-reuse, visibility, and retirement boundaries in the canonical philosophy and compact loaded workflow.
- Integrate candidate discovery into ordinary Facts foraging without a separate mandatory search stage, receipt, or skill load; a found source-verified fit cannot be duplicated without a contract/total-cost reason.
- Add one non-completing value progress fact through ordinary progress or handoff only when a value unit reaches its own current oracle and consumer boundary; parent/root completion and the existing delivery-checkpoint process remain separate.
- Add a pinned development-only TypeScript production-reachability check using explicit reviewed roots, production-mode exclusion of tests, stable machine-readable findings, exact justified baseline rows for pre-existing debt, stale-baseline removal, and fail-closed analyzer/config diagnostics.
- Require last-consumer removal to retire newly orphaned supported internal code; preserve public, plugin, CLI, reflective, or external behavior only through current explicit roots, with unsupported cases reported as `unknown`.
- Define bounded knowledge-value freshness through current owner/source links, fingerprints, and executable validation where possible; structure alone never proves semantic documentation accuracy.
- Add a portable policy: use a fitting project-native dead-code/documentation mechanism when available, otherwise retain source verification and report automatic assurance `unknown` without claiming universal enforcement.
