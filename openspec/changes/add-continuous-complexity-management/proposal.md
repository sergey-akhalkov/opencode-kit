## Why

The kit prevents many local complexity regressions, but it has no lightweight,
project-neutral loop that lets a developer verify whether a real change can still be
understood and made through a small cohesive owner and a useful simple interface.
Complex projects can therefore remain locally compliant while onboarding paths,
competing extension surfaces, evidence noise, and cross-module change cost grow until
safe development requires excessive context.

The `pmac-emulator` diagnostic case makes the gap concrete: useful typed core/facade
boundaries coexist with a boilerplate root entrypoint, two public execution paths, very
large mixed owners, and corpus/evidence/spec surfaces that dominate generic inventory
and search. The required solution is a reusable development practice for any project;
that repository is one bounded case study, not the product or proof of universality.

## What Changes

- Add one project-neutral continuous complexity-management contract with three
  proportional modes: the existing near-zero-cost main-owned change delta check, one
  thin on-demand focused comprehension/refactoring skill when concrete pressure appears,
  and an explicit review-only whole-project assessment that reuses the exhaustive audit
  and ledger owners.
- Define an Architecture Comprehension Map and one representative Change Rehearsal.
  They identify the current outcome, cohesive owners, consumer entrypoints, intended
  extension surface, hidden internals, effect/error boundaries, proof entrypoints,
  minimal context set, and expected edit set without requiring one fixed project
  language or documentation path.
- Admit an abstraction, facade, module, library, or framework only when a current
  consumer or evidence-backed change axis exists and the candidate reduces the
  concepts, internals, or scattered edits needed for the same realistic scenario.
  Reject pass-through layers, option matrices, hidden effects, and flexibility for
  hypothetical variants.
- Reuse the existing `code-quality-audit`, `architecture-and-change-locality`,
  `simplicity-and-reuse`, and `codebase-audit-loop` owners at their current boundaries.
  Add one main-executed focused skill rather than overloading the post-change quality
  audit, and do not add a generic architect, another Practice Owner, or a mandatory
  reviewer on every task.
- Add a deterministic, project-neutral complexity-foraging inventory that reports only
  explicit repository facts: declared scope and exclusions, source/test/component and
  manifest candidates, entrypoint/documentation/proof candidates, file/count/navigation
  signals, and `unknown`/`unreadable`/`unsupported` states. It does not score complexity,
  infer architecture quality, select a refactor, or treat line count as a verdict.
- Recheck an admitted refactor with the same Change Rehearsal and representative runtime
  proof. Completion requires preserved behavior and a smaller or clearer consumer
  context/change surface; moving code into more files without that benefit is not an
  improvement.
- Include the focused skill and its exact helper in the default `core` and `all` runtime
  surfaces with separate context diagnostics, context-quality checks, and loaded behavior
  gates. Provide portable instructions,
  project-facing template guidance, focused fixtures, and loaded behavior evaluation so
  the process works from the active kit against readable local repositories rather than
  depending on one target project's package scripts.
- Keep autonomous campaign remediation separate: a complexity finding becomes current
  implementation work only when it blocks the accepted change or a non-deferrable
  invariant; optional project debt remains an explicit assessment result or separately
  accepted refactoring change.

### Outcome Capsule

- **Outcome:** A developer or OpenCode main session can enter an unfamiliar readable
  project, obtain a concise architecture/owner view, rehearse one realistic change,
  identify evidence-backed complexity pressure, choose the smallest useful
  remove/narrow/reuse/extract/facade response, and prove after refactoring that the same
  consumer task is easier to understand and change without hiding behavior, effects,
  errors, or costs.
- **Operating Envelope:** Local readable repositories of any language or mixed
  toolchain; explicit target root and scope/exclusions; current kit global source;
  provider-free deterministic inventory plus model-owned semantic judgment; one current
  change scenario or explicitly bounded project assessment; project-native source,
  tests, manifests, docs, and proof commands; local planning/instruction/tool changes
  only. Unsupported ecosystems and unreadable areas remain explicit rather than
  guessed. No consumer-project production refactor is performed by this change.
- **Non-Goals:** A universal architecture score; cyclomatic/line-count quotas; proving
  that every project is simple; mandatory scheduled or every-task architecture review;
  a new Practice Owner or autonomous architect; automatic pattern selection; requiring
  microservices, interfaces, factories, dependency injection, or a fixed folder layout;
  replacing project/code-quality inventories, reuse discovery, codebase audit, OpenSpec,
  or autonomous campaigns; refactoring `pmac-emulator`; remote mutation, deployment,
  release, or protected product/API/data/security decisions.
- **Non-Deferrable Invariants:** Semantic architecture judgment remains with main and
  the already registered triggered owners; deterministic helpers report facts only;
  the current accepted outcome and runtime behavior are preserved; abstractions require
  a current consumer or named evidence-backed change axis; consumer interfaces reveal
  material effects, failures, lifecycle, and cost; compatibility surfaces are not
  removed without evidence; unrelated debt does not become mandatory scope; generated,
  vendor, corpus, and evidence roots remain visible but can be isolated from the hot
  comprehension path; unknown support never becomes a clean result.
- **Observable Proof:** Across the exact disposable partitions named under Claim And
  Evidence Scope, the installed process emits
  deterministic facts, builds a bounded focused map/rehearsal, routes only real
  architecture/reuse triggers, rejects score-driven and speculative abstractions, and
  rechecks an admitted facade/extraction against the same running scenario. A separate
  read-only `pmac-emulator` diagnostic replay must surface its useful typed/facade
  boundaries, misleading onboarding path, competing execution surfaces, mixed large
  owners, and corpus/spec search pressure without closing or broadening the generic
  partitioned claim.
- **Material Residual Risks:** Semantic findings remain model- and scenario-dependent;
  one rehearsed change can miss another subsystem's pressure; generic manifest and
  entrypoint discovery cannot understand every ecosystem; maintained architecture maps
  can drift unless rechecked against source; reducing context for one consumer can move
  cost to another; the first proof population and one external case cannot establish
  universal effectiveness or optimal architecture for every project.
- **Stop Line:** Finish one portable complexity-management workflow by extending
  existing skill/owner surfaces, one deterministic non-scoring inventory with explicit
  fallback states, one concise project-facing map/rehearsal template, focused structural
  and loaded behavior fixtures, and one read-only external case replay. Do not add a
  new Practice Owner, scheduler, campaign playbook, fuzzy metric, dependency graph
  platform, language server, persistent global complexity database, consumer-project
  refactor, or additional project migrations.

### Claim And Evidence Scope

- **Claim ID:** `continuous-complexity-management-v1`
- **Claim Class:** partitioned-domain
- **Population:** Reviewed disposable partitions `cohesive-small-project`,
  `modular-multi-component-project`, `noisy-corpus-or-evidence-project`,
  `mixed-owner-module`, `useful-current-consumer-facade`,
  `frozen-compatibility-and-current-extension`, `redundant-wrapper-chain`,
  `speculative-generic-abstraction`, `explicit-review-only-project-assessment`,
  `default-core-availability`, `unreadable-root`, and `unsupported-ecosystem`.
- **Coverage Basis:** Versioned generic repository fixtures, exact schema/order/path/
  exclusion/readback checks, matched baseline/candidate configured OpenCode sessions,
  direct source and generated-report inspection, one representative executable scenario
  before and after a fixture refactor, and one separately bounded privacy-safe external
  diagnostic that cannot complete a population member.
- **Production Path:** Existing main-owned delta check -> exact Practice Owner observation
  when a seam/sibling trigger applies -> explicit or still-unresolved comprehension
  pressure loads the focused skill -> candidate complexity-foraging inventory ->
  main-authored Architecture Comprehension Map and Change Rehearsal -> main
  disposition/refactor -> same-scenario runtime proof and focused validation. A focused
  assessment may route one materially distinct newly discovered trigger to its existing
  owner but never re-launches it for the same fact. Explicit exhaustive review routes
  directly to the existing codebase audit/ledger and starts focused mode only for a
  separately admitted subsystem refactor when those exhaustive owners are discovered;
  otherwise project mode reports unavailable without approximating coverage.
- **Comparison Paths:** Current touched-file locality and line-band inventory versus the
  candidate focused workflow on the same loaded disposable-project boundary; baseline
  versus refactored fixture; useful facade versus pass-through wrapper; clean source
  scope versus corpus/evidence-noisy scope; direct focused routing versus explicit
  exhaustive routing; default core versus missing-capability regression; supported facts
  versus explicit unsupported/unreadable fallbacks.
- **Environment:** Current supported local OpenCode installation on Windows with the
  kit source, Node, Git, disposable local repositories, selected configured model, and
  one separately read-only local Rust case. No network, remote repository mutation,
  consumer deployment, release, credential change, or external product effect.
- **Real Oracle:** Actual configured OpenCode routing/output, deterministic JSON and
  Markdown readback, current source/manifests/tests, exact files and symbols required by
  the rehearsed scenario, representative fixture execution before/after refactor, and
  direct verification that material effects/errors remain visible at the consumer
  boundary. Static marker tests support but do not replace loaded behavior.
- **Unresolved Observations:** Other models/providers and host platforms; repositories
  outside reviewed fixture classes; the separate `pmac-emulator` diagnostic case;
  ecosystem-specific entrypoint/public-surface facts not implemented in the first
  inventory; long-term map drift; whether later repeated use reduces defect rate or
  total development time; and complexity axes not exercised by the selected scenario.
- **Maximum Claim:** In the exercised installed environment and reviewed project
  partitions, the process gathers stable explicit facts, produces a bounded
  architecture/change view, distinguishes useful encapsulation from speculative layers,
  and demonstrates preserved behavior with lower consumer context/change pressure for
  the represented refactor. It does not prove universal architecture quality,
  understandability for every project, optimal abstraction, or long-term productivity.

- **Automation Dividend**: required - add one deterministic project-neutral
  complexity-foraging inventory and fixture pack that materializes reviewed repository
  facts with stable ordering and explicit fallback states while leaving all semantic
  complexity, abstraction, and refactoring decisions to main and triggered owners.
- **Bounded Falsification Review**: required - project-neutral complexity workflow ownership, proportional routing, and executable proof boundary

## Capabilities

### New Capabilities

- `library-complexity-management`: Define the portable proportional complexity loop,
  Architecture Comprehension Map, Change Rehearsal, abstraction value gate, refactor
  admission, and same-scenario recheck contract.

### Modified Capabilities

- `library-change-ready-sdlc`: Integrate a low-cost complexity delta check and concrete
  context-pressure trigger into ordinary development without an every-task reviewer or
  unrelated refactoring gate.
- `library-instruction-artifacts`: Define the maintained skill/global/template routing,
  loaded behavior partitions, trigger accuracy, context-quality discipline, and
  no-scoring instruction contract for the portable workflow.
- `library-tools-architecture`: Add the deterministic complexity-foraging inventory and
  keep its explicit facts, schema, exclusions, fallbacks, and output ownership separate
  from project inventory, code-quality line bands, and semantic judgments.
- `library-runtime-surface-profiles`: Include the focused complexity skill and exact
  portable helper in default `core` and `all` surfaces with diagnostic measurements,
  context quality, and loaded behavior intact.

## Impact

- **Expected production scope:** One thin focused complexity skill, exact reverse
  stay-quiet narrowing in adjacent skill descriptions/catalogs, existing exhaustive
  audit/ledger outputs, concise consolidated global/project-facing routing, unchanged
  architecture and simplicity Practice Owner contracts, one portable inventory owner,
  runtime profiles, fixtures/tests, docs/catalogs, and loaded behavior proof. Existing
  post-change `code-quality-audit` and service-architecture design outputs remain
  separate.
- **Reuse disposition:** `reuse` the main delta check, exhaustive audit/ledger, and
  existing Practice Owners; `build-minimal` one focused skill after maintenance review
  showed that extending the post-change quality skill would mix lifecycle/output
  responsibilities; `build-minimal` the fact-only inventory because no current helper
  owns its reviewed scope/candidate fact shape. Cross-project source search is
  `degraded`; the selected external case was verified directly and is evidence, not
  copied implementation.
- **Active-change boundary:** `add-autonomous-campaign-orchestration` remains the owner
  of multi-day P0/P1 audit remediation and `add-foundation-integrity-autorecovery`
  remains the owner of foundation contradiction recovery. Implementation must serialize
  or explicitly transfer any overlapping instruction, proof, or tool surface; this
  change does not edit either active change.
- **Compatibility/dependencies:** No product public API, protocol, persisted consumer
  data, external package, deployment surface, or remote interface is added. Existing
  skill names and inventory outputs remain compatible. The new skill/helper become
  explicit default-core surfaces; changed loaded artifacts require a new OpenCode
  process before use. `replace-instruction-limits-with-context-quality` must apply
  first, or this change must explicitly rebase on its context-quality contract before
  mutation.
- **Profile:** `Material` because later implementation changes loaded global development
  instructions and cross-project lifecycle/refactoring behavior. Planning alone remains
  `Development-Stage: development`.
