# Proof Tool Inventory

Reusable production proof runners, capture/evaluator utilities, and cleanup helpers live here. Temporary directories may hold disposable server state and raw evidence bundles, but not the only source copy of a proof tool.

`work-campaign.ts` also maintains the provider-free controller lane:
`npm run proof:work-campaign -- --mode controller --candidate-id <id> --evidence-root <absolute-new-path>`.
It exercises production `preflight`/`run`/`status`/`stop`/`replay` over disposable Git/OpenSpec projects, including invalid-definition, dirty-worktree, active-change, and unknown-writer controls. Fixture setup records its local Git/OpenSpec initialization and commits separately. The controller itself permits read-only Git/OpenSpec inspection and contained campaign state/evidence/report writes only; provider, OpenCode, mission, source, controller Git/OpenSpec mutation, host, archive, checkpoint, remote, credential, installation, and protected effects remain zero. The create-new bundle preserves command exits, transition order and refs, frozen-wave/report facts, source identities, cleanup, and an offline-replayable evaluator result.

The task-5.2 provider-free population lane is:
`npm run proof:work-campaign -- --mode population --candidate-id <id> --environment-id <id> --input-root <configured-capture-path> --evidence-root <absolute-new-path>`.
It composes the current semantic/controller/state/materializer controls with one preserved configured capture into exactly 20 identity-bound terminal observation rows; Windows supervision remains an explicit `unknown`. Population capture makes zero model/provider/host/source effects, records all local process starts and cleanup, and uses the existing `replay` mode for zero-call reevaluation.
After a complete installed-operator capture exists, the distinct composed branch replaces `--input-root` with `--host-input-root <installed-operator-capture-path>`; only that current identity-bound proof kind may change the Windows row from `unknown` to observed.

The `consumer-outcome-regression.ts` `team-advising` extension owns the nine `STA-001` scenarios. Provider-free preflight is `npm run proof:consumer-outcome -- --mode preflight --pack team-advising --source-ref working-tree --opencode <absolute-path>`. Baseline/candidate capture adds `--mode baseline|capture --candidate-id <id> --evidence-root <new-absolute-path> --session-mode configured` and, for candidate, `--baseline <bundle>`. Replay/evaluate uses `--mode replay|evaluate --pack team-advising --baseline <bundle> [--candidate <bundle>]` and makes zero configured calls. Each arm is bounded to ten root turns; permissions admit only scenario-listed tasks/skills, bounded fixture writes, and Node proof. Bundles preserve sanitized root/advisor/specialist/skill/catalog identity facts, changed paths, writer closure, source/model/profile identity, proof, and terminal cleanup. The maximum claim remains the reviewed population under the captured identity; it does not grade prose or claim universal routing. The separate `--continuity` flag leaves that immutable population unchanged and runs two candidate-only actual-compaction controls: `--mode preflight|capture|replay --pack team-advising --continuity`, with capture bounded to six configured calls and replay requiring `--candidate <bundle>`.

## Operating Rules

- `session-completion-guard-restart.ts --scenario claims` reuses the runner's isolated installed server, local effect-free provider, immutable evidence, and cleanup boundary for representative-overclaim continuation, supported exact stop, truncated closure, and unchanged Ordinary Small idle behavior. It makes zero external provider calls and is not the matched configured-model proof owned by the consumer-outcome harness.
- The consumer-outcome `status-scope` pack uses one main response, one actual SDK compaction, and one reconstruction per arm. Terminal replay preserves historical capture-evaluator digests as provenance, binds both immutable arms to one current provider-free evaluator digest, and claims only the three reviewed members under recorded identities.
- The consumer-outcome `foundation-integrity` pack uses seven reviewed configured-session scenarios and twelve explicit terminal members. Baseline/candidate evaluation checks exact owner/recovery attribution, reviewed incident states, contained fixture mutations, archive/unrelated hashes, cleanup, and provider-free replay without inferring semantic relations or dependencies.
- The consumer-outcome `complexity` pack prepares exactly `useful-current-consumer-facade`. Provider-free preflight and arm-specific harness replay verify the reviewed map/rehearsal records, exact source fact diff, representative success/failure/effect behavior, one-request configured bound, fixture-only permissions/effects, and terminal cleanup. They do not establish a configured semantic outcome. Configured use is limited to one separately cleared `diagnose` invocation and never runs from validation.

- The consumer-outcome `bounded-falsification` pack uses twelve reviewed configured-session partitions, one primary request per scenario and arm, member-local request/initial-state identities, exact readiness and independent-owner attribution, explicit correction/no-finding/exemption/anti-repeat terminal rows, and a twenty-four-primary-request full-pack ceiling. Provider-free selected-member replay checks reviewed facts without inferring materiality or task fit; historical identity mismatches support characterization only, not causal improvement.
- Consumer-outcome replay/evaluate can seal stdout-equivalent JSON with `--result-path <absolute-new-path>`; the path is create-new and an existing file fails closed.
- Run `preflight` before `live` and preserve its JSON route evidence.
